# Bonsai 기능·업무 개념과 DB 설계 확인 사항

Updated: 2026-11-18

Bonsai의 전체 기능·UX를 재현한 뒤 차별화한다. 현재 단계는 `bonsai_analysis`의 분석·원본 화면과 공식 문서를 학습해 전체 기능과 데이터 요구를 정리하고, 이를 근거로 DB 스키마를 설계하는 것이다. 이 문서는 학습용 개념·기능 지도·설계 질문을 모은 안내이며 확정된 스키마나 구현 완료 목록이 아니다.

## 사용자 역할과 업무 범위

대표는 전체 업무·재무, 영업 담당자는 고객·거래·견적·후속 연락, 운영·프로젝트 담당자는 수행·일정·예산, 실무자는 작업·시간, 외부 고객은 공유 문서·청구·자료를 확인하는 시나리오로 학습한다. 이 구분은 학습용이며 Bonsai의 기본 권한 프로필 이름과 같다고 가정하지 않는다. 실제 접근 범위는 [공식 권한 안내](https://help.hellobonsai.com/en/articles/1894805-all-about-user-permissions-in-bonsai)와 계정 관찰로 대조한다.

특정 업종·직업·팀 규모로 제품을 제한하지 않는다. 최종 판매 타깃·가격과 차별화 요구는 별도 결정 사항이며, 가상 업무 예시를 제품의 지원 범위로 확정하지 않는다. 제품 방향은 [PM 036](../AGENT/PM_AGENT/DECISIONS/036_bonsai_benchmark_transition.md)을 따른다.

## 업무 개념과 연결

| 개념 | 의미와 구분할 데이터 |
| --- | --- |
| 계정·업무 공간 | 우리 조직과 내부 멤버가 일하는 데이터·권한 경계 |
| 고객 회사·연락 담당자 | 일을 맡기는 주체와 연락하는 사람; 계정 조직과 구분 |
| 거래·파이프라인 | 성사시키려는 건과 영업 단계·금액·담당자 |
| 서비스·단가표 | 재사용할 작업 항목과 가격 기준 |
| 견적(Estimate) | 이번 업무의 범위·항목·수량·단가·원가·할인 |
| 합의 문서(Document) | 고객에게 보내고 확인·서명받는 내용과 발송·수신자·버전 |
| 프로젝트 | 실제 수행할 업무 묶음과 상태·과금 방식 |
| 작업·담당자 | 해야 할 일과 배정·기한·의존 관계 |
| 시간·비용 | 실제 투입한 시간과 지출, 청구 가능 여부 |
| 예산·인력 배정 | 예상 투입량·금액과 사람의 가용량·일정 |
| 청구서(Invoice) | 고객에게 지급을 요청하는 항목·금액·기한 |
| 입금·결제(Payment) | 실제로 받은 금액·부분 입금·잔액 |
| 고객 포털 | 외부 고객이 허용된 자기 문서·청구·자료를 확인하는 공간 |
| 사용자 필드·보기 | 추가 입력 항목과 표시·필터·정렬·공유 설정 |
| 자동화·연동·보고서 | 사건에 따른 처리, 외부 연결, 업무·재무 집계 |

가상 업무 한 건을 **고객·담당자 등록 → 상담·거래 → 견적 → 문서 합의 → 프로젝트·작업 → 시간·비용 기록 → 청구·입금 → 고객 포털 확인 → 반복 업무·보고서** 순으로 따라 읽는다. 이 순서는 이해를 위한 예시다. 각 단계의 자동 연결 여부, 사람의 선택·수정, 같은 고객의 여러 거래·프로젝트 구분은 별도로 확인한다. 실제 UI 순서나 DB의 일대일 관계를 뜻하지 않는다.

## DB 설계로 연결할 확인 사항

- 고객의 공통 정보와 거래별 조건·견적·문서·수행·청구 기록을 구분한다. 관계의 필수 여부와 연결 가능한 개수는 근거를 확인해 정한다.
- 거래 수주, 프로젝트 완료, 문서 서명, 청구, 실제 입금은 각각의 상태다. 기록한 모든 시간이 청구되는 것으로 처리하지 않는다.
- 견적 계산과 고객에게 보내는 합의 문서를 구분한다. 견적에서 문서·프로젝트·작업을 만들 때 원본 참조·복사·이후 수정의 반영 범위를 확인한다.
- 반복 청구서 발행, 자동 결제 구독, 프로젝트 리테이너, OneHand 제품 이용료를 구분한다.
- 내부 멤버·외부 고객의 접근 범위와 고객 포털 공개 범위를 확인한다. 고객 포털과 OneHand 운영자용 Admin Web은 별개다.

각 기능에서 다음 질문에 답하며 화면 관찰·공식 설명·설계 판단·미확정을 나눠 기록한다.

1. 어떤 입력값과 관계를 저장하며 무엇이 필수인가? 화면의 필수 표시와 공식 API 계약이 같은가?
2. 요청 범위·가격을 어디에 기록하고, 어떤 버전으로 합의했는가? 견적 수정이 발송 문서·프로젝트·청구에 무엇을 반영하는가?
3. 한 번의 사용자 행동으로 어떤 데이터와 상태가 함께 바뀌는가? 영업 담당자의 약속을 수행자가 어디에서 확인하는가?
4. 부분 입금·취소·추가 작업의 금액과 이력은 어디에 남는가? 세금 포함·별도, 할인·통화·반올림의 기준은 무엇인가?
5. 고객과 내부 직원에게 각각 어떤 정보·행동을 허용하는가? 보관·삭제·연결 해제가 관련 기록과 포털 접근에 어떤 영향을 주는가?
6. 국가·요금제·제품 버전에 따라 달라지는 동작은 무엇인가? 미확인 조건을 DB 제약으로 고정하고 있지 않은가?

공식 공개 API는 외부 계약이며 Bonsai의 내부 DB 구조가 아니다. API에 없는 기능도 조사 범위에서 제외하지 않는다. 확인한 요구를 기존 [DB 설계안](../AGENT/SOFTWARE_AGENT/DB_SCHEMA/BONSAI_SCHEMA_PLAN.md)과 [전환 영향](../AGENT/SOFTWARE_AGENT/COMMON/BONSAI_TRANSITION_MATRIX.md)에 연결한다. 실제 DB 변경·데이터 이전·화면 구현은 설계 이후의 별도 작업이다.

| 국내·업종 요구 | 국내 PG·전자세금계산서·지역/면적별 자동 가격·현장 배차는 미확인이다. 원본 기능으로 확정하지 않는다. |
