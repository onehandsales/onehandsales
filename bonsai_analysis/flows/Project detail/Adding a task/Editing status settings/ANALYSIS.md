## 2. 플로우 목적과 연결

작업 상태의 정의 설정을 열어 상태 색상을 변경하는 흐름이다.

- 개별 작업 상태 선택 메뉴의 Settings에서 Status Settings 모달로 진입한다.
- To Do 색상을 보라색에서 주황 계열로 바꾸고 상태 업데이트 성공 메시지를 확인한다.
- 작업 자체를 다른 상태로 옮기는 행동과 상태 정의를 편집하는 행동을 구분한다.

- 상위 흐름: [Adding a task](../ANALYSIS.md)

- 폴더 위치: `bonsai_analysis/flows/Project detail/Adding a task/Editing status settings`
- 부모·자식은 Gummble 탐색 분류이며, 모든 하위 플로우가 순차 실행된다는 뜻은 아니다.
- 하위 흐름: 없음.

### 진입 조건과 확인된 종료 범위

- 진입: 첫 캡처는 **하위 작업 추가 전 작업 상세**이다. 설명은 채워져 있고 하위 작업은 없는 상태. 이 화면 이전의 인증·권한·클릭 경로는 캡처에 보이는 범위만 인정한다.
- 종료: 마지막 캡처는 **상태 정의 업데이트 성공**이다. 상태 정의 변경 성공 피드백. 기록 종료를 전체 업무의 성공·서버 저장 완료로 확대하지 않는다.
- 관련 흐름: [Adding a task](<../ANALYSIS.md>)
- 관련 흐름은 기능 연결점이다. 서로 다른 캡처를 같은 계정·같은 시각의 연속 실행으로 합치지 않는다.

- [Board Groups API](https://docs.hellobonsai.com/api/tag/board-groups): R2 본문 대조 기록(S078). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.

화면과 대조할 때는 5절의 R2 해석 및 8절의 미확인 항목을 함께 적용한다. 현재 문서에만 있는 필수값·요금제·역할·새 UI를 과거 화면의 동작으로 확정하지 않는다.

- [API 검토 범위](<../../../../FE_REVIEW.md#api-boundary>): 이 흐름의 내부 endpoint·실제 요청/응답·DB 스키마는 확인하지 않았다. 공개 API 목록에 없는 기능의 미지원 여부도 확정하지 않는다.

## 7. 데이터 모델링 시사점

다음은 관찰에 기반한 OneHandSales 구현 후보다. 기능 채택·스키마·업무 정책으로 확정하지 않는다.

- 상태 ID·라벨·색·순서·완료 의미 후보. 고정 세 값 enum으로 전체 구현을 제한하지 않는다.
- 작업의 현재 상태 참조와 상태 정의 변경 이력을 구분한다.
- FE 후보: 상태 메뉴→설정 모달, 인라인 이름, 팔레트 선택 표시, 순서 손잡이, 성공 토스트.

### 단계별 모델링 근거

- 단계 01: 부모 작업 설명과 자식 목록 후보.
- 단계 02: 현재 상태와 상태 정의 관리 기능 분리.
- 단계 03: 상태 정의 컬렉션과 완료 구분 후보.
- 단계 04: 상태 라벨과 색 토큰 후보.
- 단계 05: 상태 스타일 변경과 정렬 후보.
- 단계 06: 상태 정의 저장과 참조 화면 갱신 후보.

## 8. 미확인 사항과 검토 질문

**원본에 없는 분기·남은 범위:** 상태 설정의 범위는 계정·팀·프로젝트 중 무엇인가? 다른 프로젝트 보드를 동시에 대조한다. Done의 이름/색/순서/삭제에 어떤 제한이 있는가? 완료 집계와 함께 검증한다.

- 상태 설정의 범위는 계정·팀·프로젝트 중 무엇인가? 다른 프로젝트 보드를 동시에 대조한다.
- Done의 이름/색/순서/삭제에 어떤 제한이 있는가? 완료 집계와 함께 검증한다.
- 새 상태 추가·삭제 시 기존 작업 재배정 정책은 무엇인가? API 오류와 확인 UI를 확인한다.
- 팔레트의 정확한 색상값과 드래그 저장은 원본 이미지·실제 DOM을 대조한다.

### 단계별 미확인 사항

- 단계 01: 설명 저장 시점·하위 항목 없음의 정확한 조회 상태.
- 단계 02: Settings 권한·메뉴 키보드 접근.
- 단계 03: 각 행 편집 가능 범위·계정별 공유 범위.
- 단계 04: 정확한 색상 코드·텍스트 저장 방식.
- 단계 05: 순서 변경 결과·저장 요청·실패 처리.
- 단계 06: 보드·다른 작업 반영·권한·이력.

- 같은 계정·제품 빌드에서 시작 상태를 맞춘 뒤 해당 업무의 정상·취소·실패·재진입 결과를 검증해야 한다. 화면 목록과 이미지 검토 완료는 제품 전체 기능의 의미적 완전성이나 구현 검증 완료를 뜻하지 않는다.

### FE 구현 전 보완 (R3)

- 캡처 범위 분류: **결과**. 업무 전체의 완료 판정이 아니다.
- 목 구현·수용 기준 후보: 작업 상태 선택과 상태 정의 편집을 구분한다. 색 변경을 반영하고 새 상태·삭제·순서·공유 범위를 별도 결정한다.
- [이 흐름의 보완표](<../../../../FLOW_REVIEW_MATRIX.md#flow-9dcc612c-ab47-4cc3-a2bb-1c434c7da582>)와 [공통 웹 상태·연결 기준](<../../../../FE_REVIEW.md#fe-acceptance>)을 함께 적용한다. 캡처에 없는 동작은 Bonsai 관찰 사실로 쓰지 않고 목 가정 또는 추가 조사로 표시한다.
