## 2. 플로우 목적과 연결

시간 기록이 있는 작업의 상세 메뉴에서 아카이브하여 활성 보드에서 숨기는 흐름이다.

- 대상 Initial Chat의 패널에7초와1시간 기록이 보인다. 뒤 보드에는 같은 이름 카드가2개라 레코드 식별에 주의한다.
- 마지막 보드에는 Initial Chat1개가 남고 보관 성공 메시지가 보인다. 동일 제목의 나머지 작업까지 보관한 것은 아니다.
- 삭제 확인 흐름과 별도로 비교하며 실제 계정 보관은 실행하지 않았다.

- 상위 흐름: [Adding a task](../ANALYSIS.md)

- 폴더 위치: `bonsai_analysis/flows/Project detail/Adding a task/Archiving a task`
- 부모·자식은 Gummble 탐색 분류이며, 모든 하위 플로우가 순차 실행된다는 뜻은 아니다.
- 하위 흐름: 없음.

### 진입 조건과 확인된 종료 범위

- 진입: 첫 캡처는 **보관할 작업의 시간 기록 상세**이다. 시간이 있는 작업 상세. 배경에 같은 제목 카드2개. 이 화면 이전의 인증·권한·클릭 경로는 캡처에 보이는 범위만 인정한다.
- 종료: 마지막 캡처는 **작업 보관 성공**이다. 활성 보드에서 대상 제외. 기록 종료를 전체 업무의 성공·서버 저장 완료로 확대하지 않는다.
- 관련 흐름: [Adding a task](<../ANALYSIS.md>)
- 관련 흐름은 기능 연결점이다. 서로 다른 캡처를 같은 계정·같은 시각의 연속 실행으로 합치지 않는다.

#### 모델링 영향

- 후보와 근거: 활성 조회 필터와 작업 보관 상태 후보. 위 표시 데이터와 상태를 근거로 검토할 후보이며 확정 스키마가 아니다.
- 확정 전 확인: 아카이브 조회·복구·시간기록/보고서 유지. 소유 범위·필수값·연결 수·삭제 영향은 화면과 공식 계약을 추가 대조한다.

## 5. 업무 규칙과 데이터 변화

| 단계 | 관찰된 상태·값 | 근거의 한계 |
| --- | --- | --- |
| 01 | 시간이 있는 작업 상세. 배경에 같은 제목 카드2개. — Initial Chat/In Progress/Feb6/Joe Doe, 총01:00:07.7초와1시간 기록 모두 Joe Doe/Feb6. | 두 같은 제목 카드의ID·어떤 작업이 시간기록 보유인지. |
| 02 | 아카이브 선택 전 메뉴 상태. — 입력 항목 없음. | 보관 확인·권한·실패 안내. |
| 03 | 활성 보드에서 대상 제외. — 남은 Initial Chat In Progress/Today/JD. | 아카이브 조회·복구·시간기록/보고서 유지. |

위 표는 화면에서 보이는 상태·값이다. 성공 토스트가 있어도 수신자 접근·영수증·서버 저장을 독립 검증한 것은 아니다.

### R2 재검토에서 보완한 해석

1시간과 7초의 두 기록을 가진 작업에서 Archive 메뉴를 거쳐 보관 안내가 나타나고 같은 제목 두 카드 중 하나가 사라진다. 상단에는 7초 타이머 표시가 남는다. 시간 기록 삭제·계속 기록 가능 여부·보관함 복원은 수록되지 않았다.

### 업무 규칙과 연결 시 주의점

- 관찰: Archive와 Delete가 다른 선택지다.
- 관찰: 시간기록이 표시된 작업에서 Archive 메뉴를 사용할 수 있다.
- 관찰: 중간 확인 모달은 이3개 캡처에 없다. 제품에 확인 과정이 전혀 없다고 단정하지 않는다.
- 미확인: 기록·청구·첨부·하위 항목의 유지, 보고서 포함 여부, 복원 경로.

## 6. 공식 도움말과 API 대조

아래 URL과 5절의 문서 규칙은 **R2의 2026-11-20 대조 기록**이다. 공통 상세 대조 문서는 현재 체크아웃에 없다. R3에서 모든 URL을 다시 읽은 것은 아니며, 새로 확인한 자료와 적용 범위는 [이번 공식 자료 검토](<../../../../FE_REVIEW.md#official-sources>)에 구분했다. 과거 캡처에 현재 규칙을 소급 적용하지 않는다. 실제 계정이나 내부 API는 실행하지 않았다.

- [Tasks API](https://docs.hellobonsai.com/api/tag/tasks): R2 본문 대조 기록(S046). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.
- [작업 생성·추적 도움말](https://help.hellobonsai.com/en/articles/5182750-how-to-create-and-track-tasks-with-bonsai): R2 본문 대조 기록(S073). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.

화면과 대조할 때는 5절의 R2 해석 및 8절의 미확인 항목을 함께 적용한다. 현재 문서에만 있는 필수값·요금제·역할·새 UI를 과거 화면의 동작으로 확정하지 않는다.

- [API 검토 범위](<../../../../FE_REVIEW.md#api-boundary>): 이 흐름의 내부 endpoint·실제 요청/응답·DB 스키마는 확인하지 않았다. 공개 API 목록에 없는 기능의 미지원 여부도 확정하지 않는다.

## 7. 데이터 모델링 시사점

다음은 관찰에 기반한 OneHandSales 구현 후보다. 기능 채택·스키마·업무 정책으로 확정하지 않는다.

- 작업의 진행 상태와 아카이브 상태를 구분할 후보. 보관을 Done 전환 또는 삭제로 처리하면 관찰된 액션 차이를 잃는다.
- 이름 대신 작업ID로 대상과 연관 시간기록을 연결해야 한다.
- FE 후보: 상세 패널 메뉴→닫힘→활성 보드 대상 제외→성공 토스트.

### 단계별 모델링 근거

- 단계 01: 작업ID와 시간기록 연결·보관 영향 검토 후보.
- 단계 02: 보관 액션과 삭제 액션 분리 후보.
- 단계 03: 활성 조회 필터와 작업 보관 상태 후보.

## 8. 미확인 사항과 검토 질문

**원본에 없는 분기·남은 범위:** 보관 작업의 시간·청구 합계는 계속 포함되는가? 보관 전후 Time Tracking/인보이스를 대조한다. 복원 메뉴·필터와 복원 후 이전 상태·순서·담당자 보존을 확인한다.

- 보관 작업의 시간·청구 합계는 계속 포함되는가? 보관 전후 Time Tracking/인보이스를 대조한다.
- 복원 메뉴·필터와 복원 후 이전 상태·순서·담당자 보존을 확인한다.
- 동일 제목 두 작업 중 어떤 ID가 보관됐는지 로컬 캡처/실계정으로 확인한다.

### 단계별 미확인 사항

- 단계 01: 두 같은 제목 카드의ID·어떤 작업이 시간기록 보유인지.
- 단계 02: 보관 확인·권한·실패 안내.
- 단계 03: 아카이브 조회·복구·시간기록/보고서 유지.

- 같은 계정·제품 빌드에서 시작 상태를 맞춘 뒤 해당 업무의 정상·취소·실패·재진입 결과를 검증해야 한다. 화면 목록과 이미지 검토 완료는 제품 전체 기능의 의미적 완전성이나 구현 검증 완료를 뜻하지 않는다.

### FE 구현 전 보완 (R3)

- 캡처 범위 분류: **결과**. 업무 전체의 완료 판정이 아니다.
- 목 구현·수용 기준 후보: 보관 상태와 작업 완료 상태를 분리한다. 보관 후 시간·문서 합계·진행 타이머·복원 동작은 별도 시나리오가 필요하다.
- [이 흐름의 보완표](<../../../../FLOW_REVIEW_MATRIX.md#flow-cb1a0f7a-140a-42c9-a1a1-cae4c5d2fc9e>)와 [공통 웹 상태·연결 기준](<../../../../FE_REVIEW.md#fe-acceptance>)을 함께 적용한다. 캡처에 없는 동작은 Bonsai 관찰 사실로 쓰지 않고 목 가정 또는 추가 조사로 표시한다.
