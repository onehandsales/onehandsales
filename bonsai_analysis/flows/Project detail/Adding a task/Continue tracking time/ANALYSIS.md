## 2. 플로우 목적과 연결

이미 수동1시간이 기록된 작업에서 타이머를 이어 실행하여 별도의 추가 시간 기록을 남기는 흐름이다.

- 작업에1시간이 있는 상태에서 시작한다.
- 2초·6초 실행 캡처 이후7초와1시간 두 기록, 총1시간7초로 끝난다.
- 기존1시간 레코드에 단순 덧셈해 덮어쓴 결과가 아니라 별도 행 두 개가 보이는 점이 모델링 근거다.

- 상위 분석: [Adding a task](../ANALYSIS.md)

- 후보와 근거: 작업ID와 시간기록 연결·보관 영향 검토 후보.
- 확정 전 확인: 소유 범위·필수값·연결 수·삭제 영향은 화면과 공식 계약을 추가 대조한다.

## 5. 업무 규칙과 데이터 변화

- 관찰: 실행 중 표시값2초/6초는 기존 누적1시간과 다르다. 세션 경과 시간과 총합을 구분한다.
- 관찰: 종료 후7초 기록과1시간 기록이 두 행으로 보인다.
- 미확인: 일시정지 시 즉시 기록 생성인지 별도 완료 동작이 있었는지, 기록 수정·병합·동시 타이머 정책.

## 6. 공식 도움말과 API 대조

- [내부 시간 추적 도움말](https://help.hellobonsai.com/en/articles/2548737-tracking-time-internally-with-bonsai): 타이머의 시작·정지와 기록 제출을 설명한다. 이 캡처에서 완료 클릭은 생략되어 구체 서버전이를 확정하지 않는다.
- [Time Entries API](https://docs.hellobonsai.com/api/tag/time-entries): GET/POST `/public-api/v1/time_entries`, PATCH `/public-api/v1/time_entries/{key}`가 공개되어 있다. 이 그룹 페이지에서 실행 중 타이머 프로토콜이나 요청 필드 계약은 확인되지 않는다.

## 7. 데이터 모델링 시사점

- 기존 TimeEntry 목록과 새 TimerSession, 작업 총합을 분리하는 후보.
- 하나의 작업에 여러 시간기록이 연결되는 근거. 합계를 유일 원본으로 저장하는 설계는 개별 기록자·날짜를 잃는다.
- FE 후보: 시간 목록 펼침, 재생/정지, 세션 카운터, 정지 후 합계/행 갱신.

## 8. 미확인 사항과 검토 질문

- 타이머 일시정지만으로7초 행이 생성되는가? 시작→정지→Done을 각각 재현한다.
- 브라우저 이동·새로고침·다른 작업의 타이머 시작은 이전 세션에 어떤 영향을 주는가? 전역 타이머와 대조한다.
- 7초 기록의 요율·청구 상태·멤버·업무일자는 어디서 상속되는가? 기록 상세/API로 확인한다.
