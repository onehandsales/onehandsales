## 2. 플로우 목적과 연결

고객의 외부 의사 확인 등을 근거로 담당자가 제안서를 수동 Accepted 처리하는 UI를 분석한다.

- Sent 제안서에서 시작한다. 실제 고객이 직접 Accept한 흐름과 구분한다.
- 패키지를 선택한 후 변경불가 안내를 확인하고 수락 상태로 바뀐다.

- 상위 흐름: [Creating a proposal](../ANALYSIS.md)

- 폴더 위치: `bonsai_analysis/flows/Creating a proposal/Marking as accepted`
- 부모·자식은 Gummble 탐색 분류이며, 모든 하위 플로우가 순차 실행된다는 뜻은 아니다.
- 하위 흐름: 없음.

### 진입 조건과 확인된 종료 범위

- 진입: 첫 캡처는 **Sent 제안서 상세**이다. 발송후읽기상태. 이 화면 이전의 인증·권한·클릭 경로는 캡처에 보이는 범위만 인정한다.
- 종료: 마지막 캡처는 **수락된 제안서 상세**이다. 수락된문서읽기상태. 기록 종료를 전체 업무의 성공·서버 저장 완료로 확대하지 않는다.
- 관련 흐름: [Creating a proposal](<../ANALYSIS.md>)
- 관련 흐름은 기능 연결점이다. 서로 다른 캡처를 같은 계정·같은 시각의 연속 실행으로 합치지 않는다.

- 단계 02: 고객열람여부·문서잠금정책미확인.
- 단계 03: Edit의확인과링크무효화·권한조건미확인.
- 단계 04: 옵션전체·다중선택제약·선택초기값미확인.
- 단계 05: 알림메일/인보이스생성결과미수록.
- 단계 06: 수락주체/법적 동의 증거는 이미지로 미확인.

- 같은 계정·제품 빌드에서 시작 상태를 맞춘 뒤 해당 업무의 정상·취소·실패·재진입 결과를 검증해야 한다. 화면 목록과 이미지 검토 완료는 제품 전체 기능의 의미적 완전성이나 구현 검증 완료를 뜻하지 않는다.
