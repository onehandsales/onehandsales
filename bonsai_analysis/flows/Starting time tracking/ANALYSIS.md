## 2. 플로우 목적과 연결

사용자가 대시보드 상단에서 타이머를 시작하고 프로젝트·요율·설명을 지정한 뒤 일시정지하고 하나의 시간 기록을 완료하는 흐름이다.

- 시작: 대시보드와 상단 Track Time. 종료: 1분 16초 기록이 고객·프로젝트·설명과 함께 표시되고 새 타이머는 0초로 돌아간다.
- 주체는 로그인 사용자로 보이지만 역할·계정 요금제는 확정할 수 없다.
- Time Tracking 목록, 프로젝트 Time, 작업의 시간 기록, 인보이스의 미청구 시간 추가와 연결한다.
- FE 재현은 빈 팝오버·실행·프로젝트 선택·도움말·닫힌 실행·일시정지·완료 요약 상태를 나눠 구성한다.


- 폴더 위치: `bonsai_analysis/flows/Starting time tracking`
- 부모·자식은 Gummble 탐색 분류이며, 모든 하위 플로우가 순차 실행된다는 뜻은 아니다.
- 상위 흐름: 없음. Gummble 최상위 분류.
- 하위 흐름: 없음.

### 진입 조건과 확인된 종료 범위

- 진입: 첫 캡처는 **대시보드 — 프로젝트 타임라인과 손익 요약**이다. Dashboard가 선택되어 있으며 모달·오류·성공 토스트는 없다. 여러 플로우가 공유하는 동일한 시작 이미지다. 이 화면 이전의 인증·권한·클릭 경로는 캡처에 보이는 범위만 인정한다.
- 종료: 마지막 캡처는 **완료된 시간 기록 요약**이다. 기존 입력 폼이 기록 요약으로 바뀌었다. 기록 종료를 전체 업무의 성공·서버 저장 완료로 확대하지 않는다.
- 관련 흐름: [Time Tracking](<../Time Tracking/ANALYSIS.md>)
- 관련 흐름은 기능 연결점이다. 서로 다른 캡처를 같은 계정·같은 시각의 연속 실행으로 합치지 않는다.

### R2 재검토에서 보완한 해석

타이머는 실행 중 필드 편집과 팝오버 닫기를 허용하며 상단 경과 시간이 계속 표시된다. 프로젝트 선택 뒤 Rate 20과 Changes Saved가 보인다. 1분 16초에 일시정지하면 Done·Resume Timer가 나타나고, 마지막에는 작업을 선택하지 않은 채 메모 Creating a proposal을 가진 기록 요약이 보인다. 타이머의 일시정지·완료·청구를 서로 다른 상태로 모델링할 후보이며 실제 저장 API는 미관찰이다.

### 업무 규칙과 연결 시 주의점

- 관찰: 프로젝트를 선택하기 전에도 타이머가 실행된다. 프로젝트 없이 완료 가능한지는 미확인.
- 관찰: 프로젝트 선택 후 Changes Saved가 보이지만 모든 필드가 같은 방식으로 저장된다고 확정하지 않는다.
- 관찰: 팝오버 닫힘은 정지가 아니다. 일시정지와 Done 완료는 서로 다른 UI 상태다.
- 관찰: 요율 도움말은 요율 없는 시간 기록도 허용하는 맥락이다. 요율 필수 DB 제약을 임의로 만들지 않는다.
- 미확인: 휴지통의 삭제 범위·복구·확인 창, 동시 타이머 수, 실제 시간 계산 정밀도.

## 6. 공식 도움말과 API 대조

- [내부 시간 추적 도움말](https://help.hellobonsai.com/en/articles/2548737-tracking-time-internally-with-bonsai): R2 본문 대조 기록(S076). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.

화면과 대조할 때는 5절의 R2 해석 및 8절의 미확인 항목을 함께 적용한다. 현재 문서에만 있는 필수값·요금제·역할·새 UI를 과거 화면의 동작으로 확정하지 않는다.

## 7. 데이터 모델링 시사점

다음은 관찰에 기반한 OneHandSales 구현 후보다. 기능 채택·스키마·업무 정책으로 확정하지 않는다.

- 설계 가정: TimerSession의 실행/정지와 TimeEntry 완료 기록을 별개 상태로 표현할 후보. 별도 테이블 필요성은 전체 시간 흐름 후 결정한다.
- 설계 가정: project, optional task, description, 업무일자, 누적 시간, 단가 후보. 화면의 회색 placeholder와 실제 기본값은 구분한다.
- 설계 가정: 금액·통화·청구 상태·인보이스 연결은 시간과 청구 흐름을 합쳐 검토한다.
- FE 후보: 전역 타이머와 팝오버 상태, 필드 저장 피드백, 초 단위 표시·일시정지·완료 요약.

- 단계 01: 프로젝트·문서 참조, 기간·통화별 재무 집계, 빠른 생성 진입점 및 공통 내비게이션 후보. 메뉴 노출은 서버 권한의 증거와 구분한다.
- 단계 02: 실행 중 타이머 상태와 미청구 시간 목록을 별개로 표시하는 후보.
- 단계 03: 타이머 실행 상태, 경과 시간, 프로젝트·작업 연결, 업무일자, 요율, 메모 후보.

- 단계 05: 프로젝트의 시간 요율 기본값 후보와 시간기록 당시 요율 스냅샷 후보; 상속 규칙 미확정.

- 단계 07: 시간기록 설명 필드와 Task 관계를 분리하는 후보.
- 단계 08: 전역 타이머 표시 상태와 팝오버 열린 상태를 별도 관리하는 FE 후보.

- 단계 10: 완료 시간기록과 새 타이머 초깃값을 분리; 고객은 프로젝트에서 조회하는 후보.

## 8. 미확인 사항과 검토 질문

**원본에 없는 분기·남은 범위:** 프로젝트 없이 Done이 가능한가? 검증 환경에서 빈 값 제출로 확인하고 필수 관계를 결정한다. 시간은 서버시각·클라이언트시각 중 무엇을 기준으로 계산하는가? 새로고침·다중 탭·시간대 전환을 재현한다.

- 프로젝트 없이 Done이 가능한가? 검증 환경에서 빈 값 제출로 확인하고 필수 관계를 결정한다.
- 시간은 서버시각·클라이언트시각 중 무엇을 기준으로 계산하는가? 새로고침·다중 탭·시간대 전환을 재현한다.
- 프로젝트 변경 시 요율20이 어디서 유래하는가? 프로젝트·사용자·작업 기본 요율을 각각 바꿔 확인한다.
- 완료·삭제·재개 시 기존 기록이 수정되는가? 네트워크와 목록 ID를 비교하고 이력·중복 방지 후보를 결정한다.

### 단계별 미확인 사항

- 단계 01: 날짜와 집계의 기준 시간대, 그래프 산식, 타임라인 아이콘의 정확한 날짜 의미, 역할별 접근 권한, 홍보 노출 조건은 이 이미지로 확인할 수 없다.
- 단계 02: 조회 기간·내 시간/팀 시간 범위와 배경 데이터 변경 이유.
- 단계 03: 프로젝트 없이 완료할 수 있는지, 최초 레코드 생성 시점, 삭제 확인 과정.
- 단계 04: 권한별 노출·완료 프로젝트 포함·검색 기능.
- 단계 05: 20이 프로젝트 기본값인지 사용자 설정인지, 자동 저장 요청·실패·debounce 동작.
- 단계 06: 미입력·0의 구분 및 청구 시 요율 결정 방식.
- 단계 07: 메모 저장 시점, 줄바꿈·길이 제한, Task 신규 생성 결과.
- 단계 08: 페이지 이동·새로고침·브라우저 종료 후 연속성, 다른 기기 동기화.
- 단계 09: 일시정지와 최종 제출의 서버 상태 차이, 재개 구간 누적·동시 타이머 제한.
- 단계 10: 실제 영속 저장·새로고침 후 유지, 청구 상태·표시 목록 기간.

- 같은 계정·제품 빌드에서 시작 상태를 맞춘 뒤 해당 업무의 정상·취소·실패·재진입 결과를 검증해야 한다. 화면 목록과 이미지 검토 완료는 제품 전체 기능의 의미적 완전성이나 구현 검증 완료를 뜻하지 않는다.

### FE 구현 전 보완 (R3)

- 캡처 범위 분류: **결과**. 업무 전체의 완료 판정이 아니다.
- 목 구현·수용 기준 후보: 실행·일시정지·재개·Done과 팝오버 닫기를 나눈다. 경과 시간은 제어 가능한 시계로 관리하고 페이지 이동 시 중복 타이머를 만들지 않는다.
- [이 흐름의 보완표](<../../FLOW_REVIEW_MATRIX.md#flow-06d57391-c7a4-4f63-ba8d-078ea3af046f>)와 [공통 웹 상태·연결 기준](<../../FE_REVIEW.md#fe-acceptance>)을 함께 적용한다. 캡처에 없는 동작은 Bonsai 관찰 사실로 쓰지 않고 목 가정 또는 추가 조사로 표시한다.


### 동일 재현을 위한 남은 분석 (R4)

- 자동 저장 지연·타이머 삭제/재개·프로젝트 미선택 종료·여러 기록 스크롤은 미확인이다. 팝오버 상태별 높이와 전역 시간 동기화·도움말 겹침을 명세해야 한다.
- 공통 미완: 요소별 누락 검사, 정확한 배치·타이포그래피·색/장식·자산 대응·미노출 상태는 [12개 검토 항목](<../../SOURCE_ANALYSIS_STANDARD.md>)으로 추가 명세한다. 원본에 없는 동작은 관찰 사실과 분리한다. 이 문서의 R4 표시를 동일 재현 명세나 FE 구현 완료로 읽지 않는다.
