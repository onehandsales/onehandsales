관찰은 Gummble 캡처에서 직접 본 내용, 문서 확인은 현재 공식 도움말·공개 API, 설계 가정은 우리 구현 후보를 뜻한다. 버튼의 존재·성공 안내·실제 서버 결과를 구분한다.

## 2. 플로우 목적과 연결

여러 비용을 선택하여 분류를 한 번에 변경하고 선택·적용·종료 상태를 확인한다.

- 시작: 비용 목록. 종료: 두 비용의 분류 갱신 성공 알림과 일반 목록.
- 행위자: 비용 수정 권한이 있는 내부 사용자로 추정. 실제 역할 확인은 없다.
- 같은 선택 바에 삭제 버튼이 있지만 이 캡처는 분류 수정만 실행한 결과를 보여준다.
- 프론트 구현: 행 호버 체크, 다중 선택·개수, 고정 작업 바, Business/Personal 모달, 종료 후 선택 해제.

- 상위 흐름: [Bookkeeping](../ANALYSIS.md)

- 폴더 위치: `bonsai_analysis/flows/Bookkeeping/Bulk editing expenses`
- 부모·자식은 Gummble 탐색 분류이며, 모든 하위 플로우가 순차 실행된다는 뜻은 아니다.
- 하위 흐름: 없음.

### 진입 조건과 확인된 종료 범위

- 진입: 첫 캡처는 **Expenses 등록 목록**이다. 비용 세 행이 표시된 목록. 소개용 그림과 구분되지만 실제 거래·서버 데이터의 진위는 검증하지 않았다. 이 화면 이전의 인증·권한·클릭 경로는 캡처에 보이는 범위만 인정한다.
- 종료: 마지막 캡처는 **일괄 분류 수정 성공**이다. 2 expenses updated category successfully 알림. 기록 종료를 전체 업무의 성공·서버 저장 완료로 확대하지 않는다.
- 관련 흐름: [Bookkeeping](<../ANALYSIS.md>)
- 관련 흐름은 기능 연결점이다. 서로 다른 캡처를 같은 계정·같은 시각의 연속 실행으로 합치지 않는다.

- 단계 간 변화: 일반 목록 복귀, 두 행 Personal 변경과 성공 알림. 캡처 사이의 정확한 클릭·요청·저장 순서는 별도 관찰하지 않았다.

#### 동작과 데이터

- 화면 관찰: 선택 대상 두 행의 분류 적용과 비대상 유지가 확인된다. 전체 transaction 성공 규칙은 미확인. 정적 캡처의 UI 상태이며 실제 요청 성공·서버 영속성은 독립 검증하지 않았다.
- 공식 문서 확인: 6절에서 기능별 출처·현재 규칙·과거 화면과의 차이를 대조한다. 이 화면의 내부 API 호출은 관찰하지 않았다.
- 설계 가정: 표시된 업무 개념은 구현 후보이며 저장 방식·권한·트랜잭션을 확정하지 않는다.
- 미확인: 부분 실패·동시 변경·이미 청구된 비용의 오류 UI.

#### 모델링 영향

- 후보와 근거: 변경 대상별 결과·권한 검증·선택 해제와 캐시 갱신 후보. 위 표시 데이터와 상태를 근거로 검토할 후보이며 확정 스키마가 아니다.
- 확정 전 확인: 부분 실패·동시 변경·이미 청구된 비용의 오류 UI. 소유 범위·필수값·연결 수·삭제 영향은 화면과 공식 계약을 추가 대조한다.

### R2 재검토에서 보완한 해석

Lunch 10과 Prints 30 두 행을 선택하여 Personal로 일괄 변경한 뒤 2개 갱신 성공 안내가 보인다. Advertising 125 행은 선택되지 않았다. 첫 두 캡처 사이 Prints의 분류 변경 조작은 수록되지 않았으며, 부분 실패와 다른 페이지 선택 범위는 미확인이다.

### 업무 규칙과 연결 시 주의점

- 관찰: 선택 대상 두 행의 금액은 유지되고 분류가 Personal로 바뀐다. 비선택 행은 유지된다.
- 관찰: 선택 수가 제목·하단 문구·삭제 버튼의 단복수에 반영된다.
- 문서 확인: 이미 청구된 비용은 일괄 수정·삭제 제한이 있다. 이 캡처는 제한 오류를 보여주지 않는다.
- 미확인: 일부 대상 실패 시 전체 rollback 여부·동시 수정·전체 선택 범위·Cancel editing의 구체 결과.

## 6. 공식 도움말과 API 대조

아래 URL과 5절의 문서 규칙은 **R2의 2026-11-20 대조 기록**이다. 공통 상세 대조 문서는 현재 체크아웃에 없다. R3에서 모든 URL을 다시 읽은 것은 아니며, 새로 확인한 자료와 적용 범위는 [이번 공식 자료 검토](<../../../FE_REVIEW.md#official-sources>)에 구분했다. 과거 캡처에 현재 규칙을 소급 적용하지 않는다. 실제 계정이나 내부 API는 실행하지 않았다.

- [공개 API](https://docs.hellobonsai.com/api): R2 본문 대조 기록(S003). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.
- [비용 분류 관리](https://help.hellobonsai.com/en/articles/3184359-how-to-add-expense-categories): R2 본문 대조 기록(S013). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.
- [비용 일괄 편집](https://help.hellobonsai.com/en/articles/1865151-how-to-bulk-edit-your-expenses): R2 본문 대조 기록(S017). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.

화면과 대조할 때는 5절의 R2 해석 및 8절의 미확인 항목을 함께 적용한다. 현재 문서에만 있는 필수값·요금제·역할·새 UI를 과거 화면의 동작으로 확정하지 않는다.

- [API 검토 범위](<../../../FE_REVIEW.md#api-boundary>): 이 흐름의 내부 endpoint·실제 요청/응답·DB 스키마는 확인하지 않았다. 공개 API 목록에 없는 기능의 미지원 여부도 확정하지 않는다.

## 7. 데이터 모델링 시사점

다음은 관찰에 기반한 OneHandSales 구현 후보다. 기능 채택·스키마·업무 정책으로 확정하지 않는다.

- 설계 가정: 명시적 대상 ID 배열과 적용할 분류 ID를 가진 일괄 변경 명령 후보.
- 설계 가정: 이미 청구됨 상태에 따른 변경 가능성 검증. 화면의 Non-billable과 이미 청구됨을 같은 상태로 취급하지 않는다.
- 선택 집합은 UI 상태이며, transaction 범위·버전 충돌·개별 결과는 실제 계약 확인 전 미확정.

### 단계별 모델링 근거

- 단계 01: 비용·분류·프로젝트 청구 상태·첨부·반복 관련 후보.
- 단계 02: 선택 대상 ID 집합과 표시 데이터의 분리.
- 단계 03: 선택 상태와 명령 대상 목록 후보.
- 단계 04: 다중 비용 ID와 작업별 결과 후보.
- 단계 05: 일괄 수정 대상 집합과 공통 변경값 후보.
- 단계 06: 비용 용도와 분류의 관계 후보; 중복 상태 저장 여부 미확정.
- 단계 07: 변경 대상별 결과·권한 검증·선택 해제와 캐시 갱신 후보.

**원본에 없는 분기·남은 범위:** 청구된 항목과 미청구 항목을 함께 선택하면 어떻게 표시·거절하는가? 혼합 상태 계정 시험. 전체 선택은 현재 페이지인가 전체 필터 결과인가? 페이지가 여러 개인 목록 조사.

- 청구된 항목과 미청구 항목을 함께 선택하면 어떻게 표시·거절하는가? 혼합 상태 계정 시험.
- 전체 선택은 현재 페이지인가 전체 필터 결과인가? 페이지가 여러 개인 목록 조사.
- 취소하면 선택만 해제되는가 폼 값도 사라지는가? 모달 닫기와 Cancel editing 각각 확인.
- 반복 비용의 한 건 분류 변경이 다음 발생분에도 반영되는가? 반복 설정과 발생분 관계 확인.

### 단계별 미확인 사항

- 단계 01: 아이콘의 정확한 의미, 정렬·검색 범위, 청구 연결과 세금.
- 단계 02: 호버로 체크박스가 나타나는지, 선택 모드 진입의 다른 경로.
- 단계 03: 전체 선택 범위·선택 0건 상태·필터 변경 시 선택 유지.
- 단계 04: 다중 페이지 선택과 권한이 다른 항목 혼합 시 처리.
- 단계 05: 분류 미선택 제출 검증·부분 성공·닫기 후 선택 유지.
- 단계 06: Personal 고정값인지 추가 하위 분류 선택 가능한지.
- 단계 07: 부분 실패·동시 변경·이미 청구된 비용의 오류 UI.

- 같은 계정·제품 빌드에서 시작 상태를 맞춘 뒤 해당 업무의 정상·취소·실패·재진입 결과를 검증해야 한다. 화면 목록과 이미지 검토 완료는 제품 전체 기능의 의미적 완전성이나 구현 검증 완료를 뜻하지 않는다.

### FE 구현 전 보완 (R3)

- 캡처 범위 분류: **결과**. 업무 전체의 완료 판정이 아니다.
- 목 구현·수용 기준 후보: 선택한 두 비용만 변경하고 비선택 행을 유지한다. 전체 선택 범위·청구 항목 혼합·실패 시 복구 방식을 가정으로 분리한다.
- [이 흐름의 보완표](<../../../FLOW_REVIEW_MATRIX.md#flow-91d17dc8-8701-405e-9133-a41f0f55c37c>)와 [공통 웹 상태·연결 기준](<../../../FE_REVIEW.md#fe-acceptance>)을 함께 적용한다. 캡처에 없는 동작은 Bonsai 관찰 사실로 쓰지 않고 목 가정 또는 추가 조사로 표시한다.


### 동일 재현을 위한 남은 분석 (R4)

- 행 hover로 체크박스가 나타나는지와 미선택/일부/전체 선택 시각 상태를 구분해야 한다. 01→02의 Prints 분류 변화는 체크박스 조작의 결과로 확정할 수 없다.
- 공통 미완: 요소별 누락 검사, 정확한 배치·타이포그래피·색/장식·자산 대응·미노출 상태는 [12개 검토 항목](<../../../SOURCE_ANALYSIS_STANDARD.md>)으로 추가 명세한다. 원본에 없는 동작은 관찰 사실과 분리한다. 이 문서의 R4 표시를 동일 재현 명세나 FE 구현 완료로 읽지 않는다.
