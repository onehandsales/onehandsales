## 2. 플로우 목적과 연결

장부 수입 한 건을 행 메뉴에서 삭제하고 목록·성공 알림의 변화를 확인한다.

- 로그인한 운영자 관점이며 역할·삭제 권한은 미확인.
- 시작: Income 목록. 종료: 대상 행이 제거되고 성공 알림이 표시된 목록.
- 첫 단일 행과 다음 세 행 사이의 등록 과정은 생략됐다. 삭제 전후 비교는 2–4단계를 기준으로 한다.
- 프론트 구현: 행 메뉴의 대상 선택, 삭제 후 목록 갱신과 토스트를 함께 다룬다.

- 상위 분석: [Bookkeeping](../ANALYSIS.md)

- 폴더 위치: `bonsai_analysis/flows/Bookkeeping/Deleting an income`
- 부모·자식은 Gummble 탐색 분류이며, 모든 하위 플로우가 순차 실행된다는 뜻은 아니다.

## 5. 업무 규칙과 데이터 변화

- 관찰: 삭제 대상은 첫 번째 수입이며 다른 두 행은 남는다.
- 관찰: Edit Income과 Delete Income이 같은 행 메뉴에 있다. 메뉴 선택과 데이터 변경은 구분한다.
- 관찰: 성공 알림과 행 제거를 확인했다. 실제 HTTP 응답, 재조회 후 지속 여부는 확인하지 않았다.
- 미확인: 확인 모달은 수록되지 않았다. 이것만으로 확인 없이 즉시 삭제한다고 단정하지 않는다.
- 미확인: 반복 일정·입금 원장·손익 보고서에 미치는 영향과 복구 가능 여부.

## 6. 공식 도움말과 API 대조

- [공식 API](https://docs.hellobonsai.com/api) 리소스 목록에서 수동 장부 수입 삭제의 전용 endpoint는 확인하지 못했다. Invoice 삭제를 동일 동작으로 대체하지 않는다.
- 공식 도움말 검색에서는 이 수입 삭제의 직접 규칙을 확인하지 못했다. 청구서 삭제로 입금·수입 보고가 바뀐다는 별도 설명을 이 흐름에 전용하지 않는다.
- 계정에서 삭제 실행·권한·오류·취소를 재현하지 않았다.

## 7. 데이터 모델링 시사점

- 설계 가정: 독립 수입 레코드의 식별자와 삭제 상태 또는 삭제 이력 후보. 물리 삭제/논리 삭제는 미확정.
- 설계 가정: 수입 변경이 재무 집계에 영향을 준다면 목록과 집계 갱신 범위를 함께 정의해야 한다.
- 반복 수입의 단일 발생분과 반복 설정의 관계는 별도 조사한다. 이 캡처로 cascade를 확정하지 않는다.

## 8. 미확인 사항과 검토 질문

- 삭제 확인창이 존재하는가? 원본 추가 화면 또는 테스트 계정에서 메뉴 선택 직후 확인.
- 삭제한 수입을 복구할 수 있는가? 도움말·재진입·삭제 이력 조사.
- 삭제 후 Overview 합계가 언제 바뀌는가? 동일 기간의 전후 집계 비교.
- 반복 수입 한 건 삭제가 향후 발생분에 영향을 주는가? 반복 규칙과 발생분 분리 여부 확인.
