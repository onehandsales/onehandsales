## 2. 플로우 목적과 연결

저장된 작업 템플릿을 선택한 프로젝트에 적용하여 실제 작업을 생성하는 흐름이다.

- 시작 Tasks 보드. New Task 옆 아이콘의 도움말은 Add from a task template.
- Select Task Template 모달에서 템플릿과 대상 프로젝트를 선택한다.
- 종료는 Consulting Project의 새 To Do 카드. 이후 캡처에는 기한이 생기지만 기한 입력 장면은 없다.

- 상위 흐름: [Tasks](../ANALYSIS.md)

- 폴더 위치: `bonsai_analysis/flows/Tasks/Adding a task (template)`
- 부모·자식은 Gummble 탐색 분류이며, 모든 하위 플로우가 순차 실행된다는 뜻은 아니다.
- 하위 흐름: 없음.

### 진입 조건과 확인된 종료 범위

- 진입: 첫 캡처는 **전체 작업 보드**이다. To Do와 Done은 비어 있고 진행 열만 데이터가 있다. 이 화면 이전의 인증·권한·클릭 경로는 캡처에 보이는 범위만 인정한다.
- 종료: 마지막 캡처는 **생성 작업에 기한이 표시된 후속 보드**이다. 기한 있는 카드 후속 상태. 기록 종료를 전체 업무의 성공·서버 저장 완료로 확대하지 않는다.
- 관련 흐름: [Tasks](<../ANALYSIS.md>)
- 관련 흐름은 기능 연결점이다. 서로 다른 캡처를 같은 계정·같은 시각의 연속 실행으로 합치지 않는다.

- 확정 전 확인: 기한 설정 경로·연도·시간대·자동계산 여부. 소유 범위·필수값·연결 수·삭제 영향은 화면과 공식 계약을 추가 대조한다.

## 5. 업무 규칙과 데이터 변화

| 단계 | 관찰된 상태·값 | 근거의 한계 |
| --- | --- | --- |
| 01 | To Do와 Done은 비어 있고 진행 열만 데이터가 있다. — 검색 placeholder Find a task. In Progress에 Initial Chat / Design Project with Doe Studio / Yesterday / JD 카드 한 개. | 보드 드래그·새 작업 기본 상태·필터/뷰 선택지. |
| 02 | 이전 보드와 달리 기존 카드가 Done에 있다. — 카드 Initial Chat가 Done 열. 검색은 비어 있음. | 아이콘 클릭·기존 상태변경의 정확한 과정. |
| 03 | 초기 선택 전. 버튼은 초록색으로 보인다. — 두 선택 모두 Select…; 필수 별표는 없음. | 빈 제출·템플릿 목록·프로젝트 권한 필터. |
| 04 | 프로젝트 선택 전 중간 상태. — Template Name=Default Task; Project 미선택. | 실제 disabled 여부·필수 검증 발생 시점. |
| 05 | 대상 선택 완료 상태. — Default Task / Consulting Project 두 값이 선택됨. | 템플릿 구성 개수 표시·미리보기·다른 프로젝트 중복 적용. |
| 06 | 새 작업1개가 To Do에 나타남. — Update company guideline / Consulting Project / No due date. 새 카드 담당자 아바타는 보이지 않음. | 실제 담당자 없음 여부·생성 ID·작업 상태 기본값 규칙. |
| 07 | 기한 있는 카드 후속 상태. — 새 카드 기한이 No due date에서 Feb09로 바뀜. 제목·프로젝트·열은 유지. | 기한 설정 경로·연도·시간대·자동계산 여부. |

위 표는 화면에서 보이는 상태·값이다. 성공 토스트가 있어도 수신자 접근·영수증·서버 저장을 독립 검증한 것은 아니다.

### R2 재검토에서 보완한 해석

Default Task·Consulting Project 선택 뒤 To Do에 Update company guideline이 생성되고 성공 토스트가 나타난다. 이후 No due date가 Feb 09로 바뀌지만 기한 지정 과정은 없다. 기존 Initial Chat의 In Progress→Done 변경도 중간 조작이 수록되지 않아 템플릿 적용 효과로 묶지 않는다.

### 업무 규칙과 연결 시 주의점

- 관찰: 템플릿 이름과 프로젝트를 별도로 선택한다. 템플릿을 수정하는 화면과 프로젝트 작업 생성은 다른 액션이다.
- 관찰: 템플릿만 고른 상태의 생성 버튼은 연한 색, 두 선택 후 진한 색. disabled 속성·검증은 직접 확인하지 않았다.
- 관찰: 생성 직후 No due date, 후속 캡처 Feb09. 템플릿이 자동으로 Feb09를 설정했다고 추정하지 않는다.
- 미확인: 반복 적용 시 중복 방지·여러 작업 생성의 원자성·담당자/첨부/하위 작업 복사.

## 6. 공식 도움말과 API 대조

아래 URL과 5절의 문서 규칙은 **R2의 2026-11-20 대조 기록**이다. 공통 상세 대조 문서는 현재 체크아웃에 없다. R3에서 모든 URL을 다시 읽은 것은 아니며, 새로 확인한 자료와 적용 범위는 [이번 공식 자료 검토](<../../../FE_REVIEW.md#official-sources>)에 구분했다. 과거 캡처에 현재 규칙을 소급 적용하지 않는다. 실제 계정이나 내부 API는 실행하지 않았다.

- [Templates API](https://docs.hellobonsai.com/api/tag/templates): R2 본문 대조 기록(S032). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.
- [Tasks API](https://docs.hellobonsai.com/api/tag/tasks): R2 본문 대조 기록(S046). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.
- [Task templates 도움말](https://help.hellobonsai.com/en/articles/11488590-leveraging-task-templates): R2 본문 대조 기록(S091). 공통 상세 원문은 현재 없으며, 이 문서에 남은 규칙·한계는 5·8절에서 확인한다.

화면과 대조할 때는 5절의 R2 해석 및 8절의 미확인 항목을 함께 적용한다. 현재 문서에만 있는 필수값·요금제·역할·새 UI를 과거 화면의 동작으로 확정하지 않는다.

- [API 검토 범위](<../../../FE_REVIEW.md#api-boundary>): 이 흐름의 내부 endpoint·실제 요청/응답·DB 스키마는 확인하지 않았다. 공개 API 목록에 없는 기능의 미지원 여부도 확정하지 않는다.

## 7. 데이터 모델링 시사점

다음은 관찰에 기반한 OneHandSales 구현 후보다. 기능 채택·스키마·업무 정책으로 확정하지 않는다.

- 템플릿 정의와 프로젝트 작업 인스턴스의 분리 후보. 적용 명령은 템플릿ID·대상 프로젝트ID를 요구하는 UI다.
- 생성 배치ID·원본 템플릿 추적·중복 요청 방지는 후보이며 제품 규칙으로 확정하지 않는다.
- 기한 없는 상태가 관찰되므로 모든 작업에 기한을 강제하는 설계는 근거가 없다.
- FE 후보: 분할 버튼의 도움말, 두 선택 폼과 가능 상태, 성공 토스트, 보드에 새 카드 반영.

### 단계별 모델링 근거

- 단계 01: 작업 상태·제목·프로젝트·담당자·기한과 상태별 정렬 후보.
- 단계 02: 템플릿 적용 전역 액션과 보드 업무 상태 분리.
- 단계 03: 적용 대상 template_id·project_id 후보.
- 단계 04: 의존 선택 입력과 생성 가능 UI 상태 후보.
- 단계 05: 템플릿 적용 명령 입력 후보.
- 단계 06: 실제 작업 인스턴스 생성, nullable 기한, 템플릿 출처 후보.
- 단계 07: 작업의 기한 변경과 적용 당시 초깃값을 별도로 기록할 후보.

## 8. 미확인 사항과 검토 질문

**원본에 없는 분기·남은 범위:** 템플릿 적용 시 첨부·하위 작업·상태·담당자가 어떻게 복사되는가? 생성 작업 상세에서 원본과 대조한다. 두 번 적용하면 두 세트가 생기는가? 반복 적용과 네트워크 재시도는 별도로 검증한다.

- 템플릿 적용 시 첨부·하위 작업·상태·담당자가 어떻게 복사되는가? 생성 작업 상세에서 원본과 대조한다.
- 두 번 적용하면 두 세트가 생기는가? 반복 적용과 네트워크 재시도는 별도로 검증한다.
- 기한 Feb09가 생긴 누락된 편집 경로를 추가 캡처로 확인한다.
- 기존 Initial Chat가 In Progress에서 Done으로 바뀐 과정은 별도 상태 변경 흐름과 대조한다.

### 단계별 미확인 사항

- 단계 01: 보드 드래그·새 작업 기본 상태·필터/뷰 선택지.
- 단계 02: 아이콘 클릭·기존 상태변경의 정확한 과정.
- 단계 03: 빈 제출·템플릿 목록·프로젝트 권한 필터.
- 단계 04: 실제 disabled 여부·필수 검증 발생 시점.
- 단계 05: 템플릿 구성 개수 표시·미리보기·다른 프로젝트 중복 적용.
- 단계 06: 실제 담당자 없음 여부·생성 ID·작업 상태 기본값 규칙.
- 단계 07: 기한 설정 경로·연도·시간대·자동계산 여부.

- 같은 계정·제품 빌드에서 시작 상태를 맞춘 뒤 해당 업무의 정상·취소·실패·재진입 결과를 검증해야 한다. 화면 목록과 이미지 검토 완료는 제품 전체 기능의 의미적 완전성이나 구현 검증 완료를 뜻하지 않는다.

### FE 구현 전 보완 (R3)

- 캡처 범위 분류: **결과**. 업무 전체의 완료 판정이 아니다.
- 목 구현·수용 기준 후보: 템플릿 적용으로 새 작업 ID를 만들고 원본 템플릿을 보존한다. 후속 Feb09를 자동 기한으로 추정하지 않고 반복 적용·첨부 복사를 정한다.
- [이 흐름의 보완표](<../../../FLOW_REVIEW_MATRIX.md#flow-d348e200-5e48-4825-a646-69a6741e85d8>)와 [공통 웹 상태·연결 기준](<../../../FE_REVIEW.md#fe-acceptance>)을 함께 적용한다. 캡처에 없는 동작은 Bonsai 관찰 사실로 쓰지 않고 목 가정 또는 추가 조사로 표시한다.
