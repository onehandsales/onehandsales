## 1. 목적과 범위

현재 View 관련 테이블이 정의하는 표시 속성·필터·정렬·그룹·집계·위젯 등을 화면 구성의 기준으로 사용한다. 같은 기능을 유지하면서 헤더와 본문에서 기능을 보여주고 조작하는 위치를 조정한다.

사용자는 관리 대상이나 업무 목록을 선택하고, 현재 대상에 연결된 View를 열어 기록을 확인한다. 보기 선택은 Attio식 드롭다운을 유지한다. 화면은 과한 구분선과 설정 노출을 줄이고 본문을 넓게 사용하는 Notion 느낌으로 표현한다.

이 문서는 11개 View의 설계안이다. View enum·저장 테이블이 있다는 사실과 화면·API·집계 기능의 구현 완료를 구분한다. Attio·Notion의 전체 기능이나 실제 내부 DB 구조를 그대로 갖췄다는 뜻은 아니다.

### 1.1. 반영한 사용자 방향

1. 기능·데이터 구조·View 설정의 의미는 현재 Attio 기반 설계를 유지한다.
2. 헤더는 대상 이름·보기 선택·즐겨찾기·조회 도구·주요 작업·보기 설정을 한 줄의 단일 영역에 배치한다.
3. 보기 선택을 노션식 탭으로 펼치지 않고 `[전체 업무 ▼]` 같은 드롭다운으로 유지한다.
4. 별 버튼은 현재 View의 즐겨찾기다.
5. 보기 설정은 단일 영역 헤더의 맨 오른쪽에 둔다.
6. 보기 설정 메뉴의 내용과 본문 조작 도구는 선택한 타입에 맞게 달라진다.
7. 이름이 같은 View로 전환하는 행동과 현재 View의 타입 변경을 구분한다.

### 1.2. 포함·제외 범위

- 포함: 공통 사이드바와 단일 영역 헤더, 보기 선택·즐겨찾기, 11개 타입별 본문, 보기 설정 메뉴, 저장·예외 상태와 스키마 대응 관계.
- 제외: Frontend·Backend 구현, API 확정, DB migration, 기본 보기·공유 권한·혼합 Object 정책 확정, 커밋.
- 회사·제품·영업 파이프라인·프로젝트는 예시다. 모든 사용자에게 강제할 전역 도메인이 아니다.
- 도식은 공간 배분과 정보 우선순위를 표현한다. 폰트·색상·정확한 픽셀 크기와 모바일 화면은 별도 구현 설계에서 확인한다.

## 2. 공통 단일 영역 헤더

### 2.1. 한 줄 안의 기능 배치

| 위치 | 배치 순서 | 역할 |
| --- | --- | --- |
| 왼쪽 | 현재 Object/List의 표시 이름 → 현재 View 선택 드롭다운 → 즐겨찾기 | 대상과 현재 보기의 맥락을 함께 보여준다. |
| 오른쪽 | 검색·필터·정렬 등 필요한 조회 도구 → 추가 드롭다운 자리 → 주요 작업 → 보기 설정 | 조회와 작업을 한 줄에서 수행한다. 보기 설정은 맨 오른쪽에 둔다. |

헤더는 하나의 수평 행으로 구성한다. 대상 이름 옆에 보기 선택과 즐겨찾기를 붙이고, 같은 행 오른쪽에 조회 도구와 기록 추가·원본 데이터 확인·대시보드 편집 등의 주요 작업을 배치한다. 제목 전용 행이나 별도 조회 도구 행으로 나누지 않는다.

- 버튼의 기능과 데이터 저장 의미는 유지하고 화면 배치만 변경한다. 이 통합 때문에 DB 구조나 API 계약을 변경하지 않는다.
- 공간이 부족하면 검색을 아이콘으로 줄이고 긴 대상·보기 이름에 말줄임을 적용하는 방향으로 구현한다. 세부 너비와 반응형 표현은 후속 화면 구현에서 정한다.
- 미정 추가 드롭다운은 2.2절의 자리만 유지한다. 역할이나 표시 여부를 이 배치 변경으로 확정하지 않는다.

### 2.2. 우측 추가 드롭다운의 미정 상태

사용자가 확정한 단일 영역 헤더의 배치는 다음과 같다.

```text
영업 파이프라인  [전체 업무 ▼] [☆]    [검색] [필터] [정렬: 마감일 ↑] [단계별 진행 ▼*] [+ 기록 추가] [보기 설정 ▼]
```

여기서 오른쪽 `[단계별 진행 ▼]`의 기능은 아직 정해지지 않았다. 왼쪽 보기 목록에도 같은 이름의 View가 있으므로 두 버튼이 같은 View 선택인지, 다른 조작을 위한 것인지 후속 확인이 필요하다.

- 공통·표·칸반 도식은 요청 문구를 보존해 `[단계별 진행 ▼*]`로 표시한다.
- 나머지 타입은 같은 위치를 `[추가 도구 ▼*]`라는 임시 표기로 표시한다.
- `*`는 기능·이름이 미정인 자리라는 문서 주석이다. 실제 제품의 확정 라벨이나 활성 기능이 아니다.
- 이 자리를 다른 View 선택, View 타입 변경, 그룹 기준 변경 등으로 임의 연결하지 않는다.
- 우측 추가 드롭다운과 관계없이 실제 보기 선택은 왼쪽 드롭다운, 실제 타입별 설정은 맨 오른쪽 보기 설정으로 설명한다.
- 후속 헤더 구현 전에 이 컨트롤의 역할·라벨·표시 여부를 정해야 한다. 그 외 헤더 배치와 11개 타입의 도식은 이 문서로 검토할 수 있다.

### 2.3. 본문 도구와 공통 헤더의 구분

달력의 날짜 이동, 타임라인의 시간 축, 지도의 확대·축소 등은 해당 본문 가까이에 둔다. 본문에 필요한 도구 줄은 해당 View의 본문 조작 영역이며, 별도 공통 헤더 행으로 추가하지 않는다.

반대로 검색·정렬처럼 의미가 없는 도구를 모든 타입에 일괄 노출하지 않는다. 차트·피벗은 집계와 원본 확인, 대시보드는 위젯 조회·편집을 중심으로 구성한다.

## 3. 보기 선택·즐겨찾기·설정

### 3.1. 왼쪽 보기 드롭다운

```text
┌────────────────────────────────────────────┐
│ ⌕ 보기 검색                                │
├────────────────────────────────────────────┤
│ ✓ 전체 업무                         표     │
│   단계별 진행                       칸반   │
│   담당자별 업무                     목록   │
│   이번 달 마감                      표     │
├────────────────────────────────────────────┤
│ + 새 보기 만들기                           │
└────────────────────────────────────────────┘
```

- 항목은 현재 Workspace와 선택한 Object/List에 소속된 `ViewDefinition` 데이터다.
- `name`은 이름, `type`은 표·칸반 등 표현 방식, `sortOrder`는 같은 소속 안의 순서에 대응한다.
- 선택하면 현재 View ID와 그에 연결된 설정을 읽어 본문을 구성한다.
- 새 보기 만들기는 이 드롭다운 안에서 시작한다.
- 같은 타입의 View도 필터·정렬·표시 속성을 달리해 여러 개 만들 수 있다.
- 11개 타입을 모든 Object/List에 처음부터 하나씩 만들도록 강제하지 않는다.
- 기본 View와 마지막 선택 중 어느 것을 우선할지는 기존 문서처럼 미정으로 유지한다.

### 3.2. 별 버튼

- `☆`: 현재 View가 즐겨찾기에 등록되지 않은 상태.
- `★`: 현재 View가 즐겨찾기에 등록된 상태.
- 누르면 현재 Workspace 구성원의 즐겨찾기를 등록·해제하는 UX다.
- 전체 업무를 보고 누르면 전체 업무 View, 단계별 진행을 보고 누르면 단계별 진행 View가 대상이다.
- Object/List 자체나 개별 기록의 즐겨찾기와 혼동하지 않는다.
- 왼쪽 즐겨찾기에서 선택하면 해당 View를 바로 연다. 보기 목록에서도 같은 View를 계속 선택할 수 있다.

### 3.3. 보기 설정

보기 설정은 단일 영역 헤더의 맨 오른쪽에 유지한다. 현재 타입의 표시·그룹·형식 등 설정을 제공하고, 메뉴 내용만 타입에 따라 바뀐다.

보기 설정의 속성을 바꾸는 것과 실제 기록값을 바꾸는 것을 구분한다. 기록값은 원본 또는 업무값에 저장하고, 열 너비·필터·정렬 등은 해당 View의 설정으로 저장한다.

## 4. 예시 데이터

### 4.1. 영업 파이프라인

| 회사 | 진행 단계 | 담당자 | 예상 금액 | 마감일 |
| --- | --- | --- | --- | --- |
| A회사 | 상담 중 | 김영업 | 500만원 | 2026-10-22 |
| B회사 | 제안 중 | 이영업 | 300만원 | 2026-10-23 |
| C회사 | 계약 완료 | 박영업 | 800만원 | 2026-10-24 |
| D회사 | 상담 중 | 이영업 | 200만원 | 2026-10-26 |
| E회사 | 제안 중 | 김영업 | 400만원 | 2026-10-27 |

- 전체 업무 5건, 금액 합계 2,200만원.
- 단계별 금액: 상담 중 700만원, 제안 중 700만원, 계약 완료 800만원.
- 담당자별 금액: 김영업 900만원, 이영업 500만원, 박영업 800만원.
- 담당자는 이 예시에서 Workspace 구성원이다. 관리 대상인 외부 담당자 기록과 같은 의미로 고정하지 않는다.
- 회사명은 원본 기록 정보, 진행 단계·담당자·금액·마감일은 이 List에서 관리하는 업무값의 예시다.
- 달력의 2026-10-19~25에는 A·B·C회사 3건이 표시된다.
- 계약 완료 상태의 예상 금액을 실제 매출로 임의 해석하지 않는다.

### 4.2. 타입별 보조 예시

- 갤러리: 제품 3개, 원화 가격과 제품 설명이 있는 텍스트 카드.
- 타임라인: 시작·종료 날짜는 마감일과 별도 속성이다. A 10/20~26, B 10/21~28, C 10/19~24, D 10/22~29, E 10/23~30.
- 간트: 요구사항 정리 10/19~20·100%, 도입 설계 10/21~23·60%, 제안 검토 10/26~27·0%, 계약 준비 10/28~30·0%. 업무 4건과 연결 3개의 예시다.
- 지도: A 서울 강남, B 서울 마포, C 부산 해운대, D 인천 연수에 사용할 수 있는 좌표가 있고 E는 위치 미설정인 예시다.
- 이 값들은 문서용 데이터다. 실제 DB에 예시 기록을 넣지 않는다.

## 5. 11개 View 타입별 화면

모든 전체 화면은 같은 단일 영역 헤더를 사용한다. 대상 이름·보기 드롭다운·별 버튼은 왼쪽에, 타입별 조회 도구·주요 작업·보기 설정은 같은 행 오른쪽에 둔다. 보기 설정은 맨 오른쪽에 유지한다. 각 도식의 `*` 표시는 2.2절의 미정 자리다.


### 5.1. TABLE — 표

많은 업무를 비교하고 셀에서 값을 빠르게 수정한다.

#### 전체 화면

```text

│                      ├───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ [홈]        [검색]   │                                                                                                                       │
│                      │  선택 회사명                   진행 단계          담당자         예상 금액        마감일                              │
│ 알림                 │  ─────────────────────────────────────────────────────────────────────────────────────────────────────                │
│ 메모                 │  □    A회사                    상담 중            김영업         500만원          10월 22일                           │
│ 할 일                │  □    B회사                    제안 중            이영업         300만원          10월 23일                           │
```

#### 현재 스키마와 구현 경계

## 6. 공통 상세·저장·예외 상태

### 6.1. 오른쪽 상세 패널

현재 View의 위치와 필터를 유지한 채 기록을 연다. 원본 기록 정보와 List 업무 정보를 구분한다.

```text
┌────────────────────────────────────────────────┐
│ A회사                        [이전] [다음]     │
├────────────────────────────────────────────────┤
│ 회사 정보                                      │
│ 회사명       A회사                             │
│ 업종         제조                              │
│ 대표 연락처  02-1234-1000                      │
├────────────────────────────────────────────────┤
│ 영업 파이프라인 업무 정보                      │
│ 진행 단계    [상담 중 ▼]                       │
│ 담당자       [김영업 ▼]                        │
│ 예상 금액    [5,000,000원]                     │
│ 마감일       [2026.10.22]                      │
├────────────────────────────────────────────────┤
│ [이 업무 목록에서 빼기]                        │
└────────────────────────────────────────────────┘
```

- 회사 정보 수정은 같은 원본을 사용하는 다른 화면에도 반영된다.
- 업무 정보는 해당 ListEntry의 값을 수정한다.
- 업무 목록에서 빼기와 원본 기록 삭제를 구분한다. 목록에서 제외했다고 원본을 함께 삭제하지 않는다.
- 이전·다음은 현재 View의 필터·정렬 맥락에서 이동한다.
- 메모·댓글·활동 이력을 현재 스키마로 구현된 기능처럼 추가하지 않는다.

### 6.2. 저장 상태

```text
평소
영업 파이프라인  [전체 업무 ▼] [☆]    [검색] [필터] [정렬] [추가 도구 ▼*] [+ 기록 추가] [보기 설정 ▼]

보기 설정 변경 후
영업 파이프라인  [전체 업무 ▼] [☆]    [검색] [필터 2] [정렬 1] [되돌리기] [보기 저장] [추가 도구 ▼*] [+ 기록 추가] [보기 설정 ▼]
```

| 변경 대상 | 저장 의미 |
| --- | --- |
| 연락처·금액·날짜·상태 등 | Record 또는 ListEntry의 실제 값 수정 |
| 열 너비·표시 속성·필터·정렬·그룹 | 현재 View의 설정 수정 |
| 새 보기 만들기·새 보기로 저장 | 별도 View 생성 |
| 즐겨찾기 | 현재 WorkspaceMember의 바로가기 등록·해제 |
| 위젯 배치 | 대시보드 위젯 설정 수정 |
| 업무 의존 관계 | Record 또는 ListEntry 사이의 실제 연결 수정 |

보기 설정을 변경하면 같은 헤더 행 오른쪽에 되돌리기·보기 저장을 표시하는 방향이다. 별도 저장 도구 행은 만들지 않는다. 저장 버튼의 노출은 UX 제안이며 공유 권한·자동 저장 정책을 새로 확정하지 않는다. 임시 필터 변경과 저장된 보기의 변경을 구분하고, '모두에게 저장' 같은 의미를 권한 정책 없이 가져오지 않는다.

### 6.3. 예외 상태

| 상황 | 표시 내용 예 | 다음 행동 |
| --- | --- | --- |
| 기록 없음 | 아직 등록한 기록이 없어요. | 기록 추가 |
| 필터 결과 없음 | 조건에 맞는 기록이 없어요. | 필터 조정·초기화 |
| 날짜 속성 미연결 | 표시할 날짜를 선택해 주세요. | 날짜 속성 선택 |
| 날짜값 미설정 | 날짜가 없는 기록이 있어요. | 미설정 목록 열기 |
| 위치 좌표 없음 | 위치를 확인해 주세요. | 위치 입력·확인 |
| 집계 기준 미연결 | 계산할 기준을 선택해 주세요. | 보기 설정 열기 |
| 값 저장 실패 | 저장하지 못했어요. 다시 시도해 주세요. | 입력 유지·재시도 |
| 보기 조회 실패 | 기록을 불러오지 못했어요. | 다시 시도 |
| 일부 위젯 실패 | 이 위젯을 불러오지 못했어요. | 위젯별 다시 시도 |

로딩·실패·빈 결과를 구분한다. 드래그 조작에는 날짜 입력·상태 선택·연결 선택 같은 대체 경로를 제공한다. 별과 아이콘에는 의미를 알 수 있는 이름과 키보드 접근을 제공하는 방향으로 구현한다.

## 7. 현재 View 스키마와의 대응

| 화면 기능 | 현재 저장 구조 |
| --- | --- |
| 보기 이름·타입·설명·순서·소속 | `ViewDefinition` |
| 표시 속성·역할·라벨·너비·숨김·형식 | `ViewAttributeSettingDefinition` |
| AND/OR 필터 그룹 | `ViewFilterGroupDefinition` |
| 필터 조건·비교값·다중값 일치 | `ViewFilterConditionDefinition` |
| 정렬·우선순위 | `ViewSortDefinition` |
| 일반 그룹·차트 계열·피벗 행과 열 | `ViewGroupDefinition` |
| 개별 그룹의 순서·이름·숨김·접힘 | `ViewGroupSettingDefinition` |
| 대시보드의 원본 View 참조·배치 | `ViewWidgetDefinition` |
| 업무의 선행·후행 연결 | `ViewWorkDependencyDefinition` |
| 구성원의 View 즐겨찾기 | `ViewFavoriteDefinition` |

`ViewDefinition`의 `type`에 따라 본문과 설정 메뉴를 구성한다. 이 테이블과 하위 설정이 무엇을 어떻게 보여줄지 결정하고, 실제 기록은 기존 Record·ListEntry 값 구조에서 읽고 수정한다.

- `sourceScope`의 `RECORD`·`LIST_ENTRY`와 참조 경로로 읽을 속성의 출발점을 구분한다.
- 탭을 쓰지 않는 드롭다운 표현이나 단일 영역 헤더 재배치 때문에 새로운 View 데이터 모델을 만드는 것으로 접근하지 않는다.
- `configJson`·`formatJson`·`layoutJson`·`groupKeyJson`의 구체적인 계약은 필요하다. 저장 공간만으로 동작이 구현되지는 않는다.
- 현재 View 관계는 기본 ID FK 중심이다. Workspace·View·Attribute 소속과 JSON 경로·타입 유효성은 추가 검증 설계가 필요하다.
- 비교 연산자·다중값·빈 값·집계 중복 처리, 기본 보기와 개인·공유 범위는 임의 확정하지 않는다.
- Object는 Record, List는 ListEntry 단위로 조회·집계하는 기준을 분명히 한다. 같은 회사가 여러 업무에 등장할 때 회사 수와 업무 수를 혼동하지 않는다.
- 현재 List에는 특정 Object로 고정하는 FK나 동일 List·Record 조합의 unique가 없다. 혼합 Object 허용·중복 등록 정책을 이 화면 예시로 확정하지 않는다.
- 이미지 업로드, 지도 연동, 과거 상태 이력, 자동 일정 조정과 협업 권한은 현재 화면 표현만으로 추가되지 않는다.
