# Solo Service QA Runbook

상태: Active
작성일: 2026-08-13

## 1. 목적

이 문서는 1인 QA 실행자가 `onehand.sales`를 실제 사용자처럼 사용하면서 기능 QA와 UX/UI QA를 함께 수행하고, 발견 즉시 보수할 항목과 기록만 남길 항목을 구분하기 위한 기준이다.

현재 서비스는 결제/구독을 제외한 대부분의 기능이 80~90% 수준으로 구현된 상태로 본다. 따라서 이번 QA의 목적은 단순 PASS/FAIL 판정이 아니라 실제 서비스화를 위해 기능을 선별하고 정리하는 것이다.

## 2. 기본 원칙

- 기능 QA와 UX/UI QA는 같은 사용 흐름에서 함께 발견한다.
- 바로 고치는 항목과 기록 후 나중에 묶어서 처리할 항목을 분리한다.
- QA 중 새 기능 아이디어가 나와도 즉시 구현하지 않고 `DEFER` 또는 `RETHINK`로 기록한다.
- 하루 단위로 QA를 마감하고, 다음 날 바로 처리할 항목만 다시 고른다.
- 기능 방향이 바뀌면 관련 문서, API 계약, FE/BE 구현 기준, regression QA 범위도 함께 갱신한다.

## 3. 실행 방식

### 3.1 1차 전체 QA

1차 QA는 고치는 시간이 아니라 전체 서비스를 실제로 한 번 써보는 시간이다.

1. `SERVICE-QA-CHECKLIST.csv`의 `우선순위=P0`부터 시작한다.
2. 각 행의 `화면/Route`에 접속해 `QA 체크`를 실제 사용자처럼 수행한다.
3. 기능 동작, API 실패, UX/UI 불편, 문구 문제를 같은 행의 `메모`에 기록한다.
4. `결과`, `판단`, `Severity`, `Issue ID`를 가능한 범위에서 채운다.
5. S0/S1이 아니면 바로 고치지 않고 다음 QA 항목으로 이동한다.

1차 QA의 목표는 모든 화면과 API를 한 번씩 확인하고, 어떤 기능을 유지/수정/개선/숨김/제거/보류할지 판단 근거를 모으는 것이다.

### 3.2 즉시 수정 예외

1차 QA 중에도 아래 항목은 바로 수정해도 된다.

- 로그인 불가
- 주요 보호 화면 진입 불가
- 저장, 수정, 삭제, 복구가 전혀 동작하지 않음
- 데이터 유실 또는 잘못된 사용자 데이터 노출 위험
- Admin 민감 정보, token, provider secret, raw response 노출
- QA 진행을 막는 빌드/런타임 오류

즉시 수정한 경우에도 CSV에는 `결과=PASS`, `판단=FIX` 또는 `IMPROVE`, `메모=수정 후 재확인 내용`을 남긴다.

### 3.3 수정 라운드

1차 전체 QA가 끝난 뒤 수정 라운드를 따로 진행한다.

1. S0/S1을 먼저 고친다.
2. 같은 화면군의 S2/S3를 묶어서 고친다.
3. 반복적으로 발견된 UX/UI 문제는 공통 패턴으로 묶어서 개선한다.
4. `HIDE`, `REMOVE`, `DEFER`, `RETHINK`는 구현 전에 제품 판단을 먼저 확정한다.
5. 수정한 항목만 2차 재QA를 수행한다.

UX/UI는 한 화면씩 즉흥적으로 바꾸지 않는다. 전체 QA에서 반복적으로 보이는 불편함을 모은 뒤, 목록/상세/form/dialog/navigation 같은 패턴 단위로 정리해서 고친다.

## 3.4 CSV 작성 예시

문제가 없으면 다음처럼 기록한다.

```text
결과: PASS
판단: KEEP
Severity:
Issue ID:
메모: Chrome desktop 1440px에서 회사 목록/검색/필터/정렬/페이지 이동 확인. 네트워크 요청 정상, 콘솔 오류 없음.
```

문제가 있으면 다음처럼 기록한다.

```text
결과: FAIL
판단: FIX
Severity: S2
Issue ID: QA-USER-COMPANY-001
메모: 검색어 입력 후 pagination 2페이지로 이동하면 /api/companies 요청에서 companyName 파라미터가 빠짐.
```

환경이나 외부 provider 때문에 확인하지 못하면 다음처럼 기록한다.

```text
결과: BLOCKED
판단: DEFER
Severity: S3
Issue ID:
메모: Google OAuth 테스트 client 미설정으로 end-to-end 확인 불가. 일반 일정 CRUD QA와 분리.
```

## 4. 즉시 수정 기준

아래 항목은 QA 흐름을 크게 끊지 않는 범위에서 바로 수정할 수 있다.

- 화면 진입이 안 됨
- 저장, 수정, 삭제, 복구가 실패함
- 명확한 오타 또는 문구 오류
- 버튼 위치, 라벨, 빈 상태처럼 10~20분 안에 끝나는 UX 문제
- 사용자가 다음 행동을 찾지 못하는 명확한 흐름 문제
- API client 경로, 요청 body, response mapping의 단순 불일치

## 5. 기록 후 묶어서 처리할 기준

아래 항목은 바로 수정하지 말고 먼저 기록한다.

- 화면 구조를 크게 바꿔야 하는 UX
- API 계약 변경이 필요한 기능
- 기능을 제거, 숨김, 유지 중 무엇으로 볼지 판단이 필요한 항목
- 여러 화면에 영향을 주는 공통 컴포넌트 수정
- 성능, 데이터 모델, migration, 운영 정책에 영향을 주는 변경
- 있으면 좋겠다는 수준의 새 기능

## 6. 기능 판단 분류

QA 이슈에는 severity와 별도로 아래 triage 값을 기록한다.

- `KEEP`: 현재 기능을 유지한다.
- `FIX`: 의도한 기능이 깨져서 고친다.
- `IMPROVE`: 방향은 맞지만 UX, API, 성능, 문구를 개선한다.
- `REMOVE`: 제품을 복잡하게 하거나 필요성이 낮아 제거한다.
- `HIDE`: 나중에 쓸 수 있지만 지금 사용자에게 노출하지 않는다.
- `DEFER`: 베타 이후 또는 별도 계획으로 미룬다.
- `RETHINK`: 기능 의도, 사용자 가치, 구현 방향을 다시 판단한다.

## 7. 기능별 반복 질문

각 기능을 확인할 때 아래 질문만 반복한다.

- 이 기능은 실제로 필요한가?
- 사용자가 업무를 끝까지 완료할 수 있는가?
- 다음 행동이 헷갈리는가?
- 기능이나 화면이 너무 복잡한가?
- 지금 숨기는 게 더 나은가?
- 베타 전에 꼭 고쳐야 하는가?

## 8. 권장 QA 순서

혼자 실행할 때는 아래 순서로 한 바퀴를 돈다.

1. 자동 검증: BE/FE typecheck, lint, build, 기본 E2E
2. 로그인, 로그아웃, 보호 라우트
3. 회사
4. 담당자
5. 제품
6. 딜
7. 일정
8. 회의록
9. Search
10. Trash
11. Import
12. Notification/Reminder
13. AI weekly report/follow-up
14. Admin Web
15. 모바일 390px/360px와 desktop 1440px UX 확인

## 9. 일일 마감

하루 QA가 끝나면 다음만 정리한다.

- 오늘 바로 수정한 항목
- 내일 바로 수정할 `FIX` 또는 높은 우선순위 `IMPROVE`
- `REMOVE`, `HIDE`, `DEFER`, `RETHINK` 판단이 필요한 항목
- 새로 발견한 S0/S1/S2
- 재검증이 필요한 기능
