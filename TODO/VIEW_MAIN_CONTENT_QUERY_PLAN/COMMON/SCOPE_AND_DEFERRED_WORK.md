# 현재 조회 범위와 후속 저장 작업

반영일: 2026-10-30. 사용자가 **현재는 주 화면 조회 API만 구현하고 필터·정렬 저장 API는 나중에 진행**하도록 범위를 지정했다. 이 문서는 현재 범위와 후속 연결의 기준이다. 기존 문서의 임시 override 검토보다 이 범위 결정을 우선한다.

## 1. 현재 Backend 구현 대상

```http
GET /api/users/me/workspaces/:workspaceId/view-definitions/:viewDefinitionId/data
```

- endpoint 하나로 11개 View Type의 본문 조회를 지원한다. 타입별 내부 조회기와 DTO를 분리한다.
- DB에 **이미 저장된** View의 필터·정렬·표시·그룹·집계·기간·위젯 설정을 읽어 실행한다.
- q/페이지/기간/지도 범위 등 API 명세에 있는 조회 매개변수는 사용할 수 있다. 임시 필터 트리·정렬 목록·보기 설정을 덮어쓰는 override는 현재 계약에 추가하지 않는다.
- Record/ListEntry와 값을 읽고 조건 평가·정렬·집계·페이지 처리를 한다. View 설정이나 원본 업무 값을 생성·수정·삭제하지 않는다.
- 기존 헤더·메뉴 GET은 재사용한다. 이를 새로 구현하거나 저장 동작을 GET에 넣지 않는다.
- 이번 Backend 완료 기준에 FE 컴포넌트 구현·지도 공급자 선정·헤더 자동 저장 연결을 포함하지 않는다. 기존 FE 계획은 후속 연결 참고로 유지한다.

**저장 API가 없어도 저장된 조건에 맞는 본문 조회를 구현하고 검증할 수 있다.** 실제 DB의 목 데이터에 저장 설정이 있으므로 이를 정상 사례로 사용하고, 누락·오류·경계 사례는 격리된 테스트 fixture로 검증한다. 테스트를 위해 실제 Workspace의 설정/업무 값을 덮어쓰지 않는다.

## 2. 사용자가 선택한 동작

| 항목 | 반영할 기준 | 적용 시점 |
| --- | --- | --- |
| 필터·정렬 변경 | DB에 저장하고 저장 성공 후 본문을 즉시 재조회. 브라우저 새로고침 후에도 유지 | 저장 API와 FE 연결을 진행하는 후속 단계 |
| 종료일 없는 일정 | 앞선 A안: Calendar는 시작일 하루 일정, Timeline/Gantt는 기간 미설정 목록. 시작일도 없으면 미설정 목록 | 현재 GET의 날짜 결과 분류 |
| List 집계 | 고유 원본 단위는 ListEntry. 같은 Record를 가리키는 Entry 둘은 두 항목이며, 해당 Record 금액을 Entry별로 집계하면 각각 한 번 기여 | 현재 GET의 원본/집계 처리 |

Entry 집계 선택은 같은 Record의 중복 Entry를 금지하는 정책이 아니다. SQL JOIN으로 한 Entry의 값이 여러 행으로 증식한 중복도 그대로 더한다는 뜻이 아니다. 다중값·다중 그룹의 기여 정책은 별도 검토한다.

종료일 없는 항목의 표시 선택은 종료 날짜의 포함/제외 경계, Timestamp 시간대, 진행률의 모든 정책까지 확정한 의미가 아니다. 해당 세부 계약은 P04에서 구분한다.

## 3. 후속 작업 목록

| 후속 기능 | 해야 할 작업 | 현재 GET와의 연결 |
| --- | --- | --- |
| 필터 구성 저장 API | 권한·필터 트리·참조·연산자를 검증하고 ViewFilterGroupDefinition/ViewFilterConditionDefinition을 원자적으로 저장 | 저장 성공 후 같은 View의 `/data` 재조회 |
| 정렬 구성 저장 API | 속성·방향·우선순위를 검증하고 ViewSortDefinition 저장 | 저장 성공 후 cursor/page를 초기화하고 `/data` 재조회 |
| FE 자동 저장·결과 갱신 | 입력 확정 시 저장, 저장 중/실패 표시, 연속 변경 순서 관리, 메뉴 캐시와 본문 갱신 | 저장 응답 이후 서버에 저장된 조건으로 조회 |
| 보기 설정 저장 | 표시 속성·그룹·타입별 설정의 별도 mutation 계약 | 후속 요구 범위에 따라 저장 후 재조회 |
| FE 11개 본문 | 기존 계획의 컴포넌트·query·반응형·접근성 구현 | 현재 GET 계약 소비 |

필터·정렬 저장 API는 **후속 작업으로 확정**, 상세 method/path/request/response/오류/동시 수정 정책은 아직 미설계다. 이전 대화의 `PUT …/filters`, `PUT …/sorts`는 전체 구성 저장 방식의 후보이며 확정된 신규 endpoint로 표시하지 않는다. 후속 구현 전에 별도 API 계약과 transaction·재시도·경합 처리 규칙을 작성한다.

후속 저장 API가 수정하는 것은 View 설정 테이블이다. 필터를 ‘금액 30만 이상’으로 바꾸어도 Record의 금액을 변경하지 않는다.

```text
현재 단계
저장된 View 설정 → 주 화면 GET → 저장 조건에 맞는 결과

후속 단계
사용자 필터/정렬 변경
  → 저장 API 검증·DB 저장
  → 저장 성공 응답
  → 메뉴 상태 갱신·기존 본문 page 초기화
  → 같은 주 화면 GET 재호출
  → 결과 갱신
```

전체 브라우저 reload는 필요하지 않다. 저장 실패와 저장 성공 후 조회 실패를 구분하고, 늦은 저장/조회 응답이 최신 선택을 덮어쓰지 않게 한다. 현재 BE-only 작업에서 기존 FE 임시 편집 UI를 임의로 비활성화하거나 저장 기능처럼 변경하지 않는다. 실제 FE 연결 시 저장 전/후 상태와 적용 여부를 명확히 표시한다.

## 4. 구현 착수 판단

**저장 API는 현재 GET 구현의 선행 조건이 아니다.** 현재 구현 범위와 기본 데이터 흐름은 정리됐다. 다만 API 계약은 아직 draft다. 저장 기능 보류를 이유로 아래 조회 계약의 미확정 항목까지 자동 승인된 것으로 처리하지 않는다.

| 현재 GET에서 착수 전에 닫을 사항 | 필요한 결정/검증 |
| --- | --- |
| 설정 실행 지원표 | source/제목 선택, 필터 연산자·값 형식·empty/ANY/ALL·정렬, 다중값/그룹·metric 지원 조합과 미지원 응답 |
| 기간·집계 세부 의미 | 확정된 Entry 단위와 기간 미설정 표시를 유지하며 날짜 경계·통화·null/0·총합 의미 명시 |
| 실행 기반 | public query Port 소유권·DI, snapshot context, cursor 보호와 설정 변경 시 처리 |
| 처리 상한 | 페이지/기간 외 scan·관계 탐색·그룹/피벗·응답 크기·실행시간의 구체적 상한과 오류 검증 |

이는 후속 저장 API를 먼저 만들거나 모든 확장 기능을 완성하라는 조건이 아니다. **다음 작업의 첫 단계는 GET의 지원 범위·기본값·실패 처리를 확정해 API-SPEC을 confirmed로 만드는 것**이다. 그 다음 공통 조회 기반과 11개 조회기를 구현한다. 기능 확장이 필요한 정책은 명시적 미지원/설정 안내 상태와 함께 후속으로 분리할 수 있으나, 전체 타입을 빼거나 임의 기본값으로 계산 결과를 바꾸지 않는다.

기술적 한도와 내부 구조는 구현자가 기존 규칙에 맞춰 구체화하고 검증한다. 사용자가 10개 결정 항목의 모든 기술 세부사항을 직접 선택해야 하는 승인 절차를 추가하지 않는다. 새로운 제품 의미가 필요한 부분만 별도로 확인한다.

현재 문서 보완은 코드 구현 착수나 배포 완료를 뜻하지 않는다. [구현 순서](GOAL-WORK-ORDER.md)와 [검토 현황](PLANNING-REVIEW.md)을 함께 따른다.
