## 1. 목적과 현재 상태

기존 범용 데이터 모델과 UX를 folk의 기능·UX를 재현하는 방향으로 전환한다. 필요한 동작을 유지하면서 데이터 모델의 복잡성을 줄이는 것이 설계 목표다. folk의 내부 DB는 공개되지 않았으므로 실제 화면·공식 동작을 근거로 우리 DB를 설계한다.

- [x] 제품·UX·Software 문서를 folk 기준으로 정리했다.
- [x] 현재 구현과 목표 설계를 구분하고 기존 모델의 유지·대체·제거 후보를 문서화했다.
- [x] 문서 검토 및 커밋을 완료했다. 기준 커밋: `faf89af6`.
- [ ] Nicelydone MCP를 통한 folk 화면 수집과 실계정 동작 대조.
- [ ] 새 화면·DB·API 계약 확정 및 구현.
- [ ] 데이터 이전과 기존 구조 제거.

현재 코드에는 Object/List/Attribute/Record/View 기반 구현이 남아 있다. 문서 전환만 완료된 상태이며, 새 folk 모델로 DB가 변경된 것은 아니다. 이전 조사에서는 Nicelydone 도구가 노출되지 않았으므로 다음 작업 시작 시 연결 상태를 다시 확인한다.

사용자 요청에 따라 계획은 이 Markdown 파일 하나로 관리한다. 단계별 결과·미확인 사항·완료 근거를 이 파일에 갱신하며, 계획 폴더나 문서를 자동으로 여러 개 생성하지 않는다. 기존 TODO 문서 및 TODO_LOG의 일괄 정리는 이번 범위에 포함하지 않는다.

## 2. 작업 원칙

### 2026-11-16 사용자 방향 보충

- 제품·UX 문서의 참고 제품은 folk로 통일한다. 과거 참고 제품명과 그 기준을 현재 문서의 본문·제목·파일명·링크에 남기지 않는다.
- 인증·사용자·Workspace는 유지 검토의 출발점으로 둔다. Workspace와 연결된 멤버·팀·행위자 및 권한 구조까지 무조건 현행 유지로 확정한 것은 아니다.
- `ObjectDefinition`, `ListDefinition`, `AttributeDefinition`, `ViewDefinition`과 관련 Record·값·옵션·관계·보기 설정 테이블은 전면 교체를 검토한다. 현재 코드가 존재한다는 이유로 기존 범용 엔진을 보존하는 것을 목표로 삼지 않는다.
- 교체할 테이블·컬럼은 **folk 화면 조사 → 작은 흐름의 mock UX → 데이터 의미·API 계약 → 물리 DB 설계**로 구체화한다. 화면에 보이지 않는 소유권·다중 소속·권한·삭제·동시 수정은 공식 문서와 실제 계정으로 대조한다.
- 화면으로 필요한 데이터를 추론할 수 있지만 folk 내부 DB를 복원했다고 표현하지 않는다. 물리 스키마와 제약은 우리 구현의 설계 결정이다.
- 기존 DB를 먼저 삭제하지 않는다. 데이터 이전 필요 여부와 새 구현으로 전환할 시점은 G03·G08에서 정한다. 전체 화면을 끝낼 때까지 DB 설계를 미루지도 않는다.

### 공통 원칙

1. 최종 목표는 folk 전체 기능·UX 대응이다. 첫 구현 범위와 최종 범위를 구분한다.
2. 특정 직군, 개인 전용 CRM, 첫 Kit 선택을 선행 조건으로 다시 도입하지 않는다.
3. 화면 캡처, 공식 문서, 실제 계정 관찰, 우리 설계 제안을 구분해 기록한다.
4. 화면을 전부 완성한 후 DB를 설계하지 않는다. 작은 흐름마다 화면·데이터·API·권한을 함께 정한다.
5. People/Companies 기본 정보와 그룹별 확장 필드를 구분하는 안을 검토한다. Custom fields/Custom objects를 모두 없애거나 기존 범용 모델을 그대로 유지하는 결론을 미리 정하지 않는다.
6. Auth/Workspace/Team 등 기존 기반은 보존을 출발점으로 삼되, folk의 공유·권한 의미와 맞는지 검토한다.
7. 테이블 삭제는 새 계약, 기존 참조, 실제 데이터 보존 요구를 확인한 후 진행한다. 이 계획 작성은 DB 초기화나 삭제 실행 지시가 아니다.
8. 한 번의 구현 작업은 아래의 작은 기능 단위와 단계 하나로 한정한다. 완료 근거 없이 체크박스를 완료 처리하지 않는다.

## 4. G00~G02: 먼저 화면과 동작 확인

### G00 — Nicelydone MCP와 조사 자료 확인

- [ ] 실제 사용 가능한 Nicelydone MCP 도구·로그인 상태를 확인한다.
- [ ] folk 화면 또는 flow를 한 번 조회하여 접근 가능 여부를 확인한다.
- [ ] 연결되지 않으면 연결 미완료로 기록하고, 확보 가능한 공식 문서·사용자 제공 캡처를 조사 자료로 구분한다.
- [ ] 조회 가능한 화면의 버전·캡처 날짜·플랜·역할·기기·언어를 기록한다. 알 수 없는 조건은 미확인으로 둔다.
- [ ] 출처별 관찰 결과를 아래 작업 기록 표에 남긴다.

완료 기준: 조회 성공 여부, 실제 확보한 자료, 추가로 필요한 자료가 명확하다. MCP 자료를 조회하지 않았다면 수집 완료로 쓰지 않는다. 자료가 부족한 화면의 동작은 확정하지 않는다. 이 단계에서는 실행 코드와 DB를 변경하지 않는다.

### G01 — 첫 흐름 조사

첫 조사·구현 흐름 제안:

```text
로그인 / Workspace 진입
  → Group 생성·선택
  → Person 또는 Company 등록·그룹에 추가
  → Table에서 조회·필드 편집
  → Pipeline에서 분류·이동
  → 상세에서 정보 확인·수정
  → 새로고침 후 상태 확인
```

- [ ] 가입·초대·온보딩과 기존 Workspace 진입의 차이를 확인한다.
- [ ] 사이드바, Group, People/Companies 탭, View의 관계를 확인한다.
- [ ] 새 연락처 생성과 기존 연락처의 그룹 추가를 구분한다.
- [ ] 입력 필드·필수값·validation·저장·취소·중복 처리·성공 후 위치를 확인한다.
- [ ] Table의 필드 추가·편집·필터·정렬·열 설정과 자동 저장 동작을 확인한다.
- [ ] Pipeline 분류 필드, 카드 이동, 열 설정과 실제 값 변경을 확인한다.
- [ ] 상세 화면과 관련 레코드 연결, 검색, 그룹에서 제거와 연락처 삭제를 확인한다.
- [ ] 정상·빈·로딩·오류·권한 제한 및 모바일 상태를 확인하거나 미확인으로 남긴다.

완료 기준: 각 핵심 동작에 출처와 데이터 영향이 연결되어 있다. 공식 문서와 화면이 다르면 차이를 기록하고 채택할 동작을 정한다. 관찰하지 않은 모바일 화면이나 삭제 동작을 추정으로 확정하지 않는다.

### G02 — 첫 흐름의 mock 화면

- [ ] G01에서 확인한 구조로 탐색·목록·상세 및 생성·편집 동선을 연결한다.
- [ ] mock 데이터임을 표시하고, 필요한 상태별 화면을 구성한다.
- [ ] 각 사용자 행동이 읽고 쓰는 데이터와 필요한 API를 함께 정리한다.
- [ ] folk 원본과 다른 배치·동작·문구를 차이 목록으로 관리한다.

완료 기준: 첫 흐름을 직접 따라가며 검토할 수 있고, mock 성공을 실제 저장 완료로 오해하지 않는다. DB 삭제·실데이터 이전은 이 단계에 포함하지 않는다.

## 5. G03~G06: 기능 단위로 설계하고 구현

첫 흐름을 다음 단위로 나누어 G03 → G04 → G05 → G06을 반복한다. 아래 분할은 조사 결과에 맞춰 조정하되 각 단위의 완료 범위를 명시한다.

| 단위 | 범위 | 먼저 연결할 동작 |
| --- | --- | --- |
| B01 | Workspace 진입·Group·Person | 사람 생성/기존 사람 추가 → 목록 → 상세 재조회 |
| B02 | Company·담당자 연결 | 회사 등록·그룹 추가 → 사람과 연결 → 양쪽에서 조회 |
| B03 | 그룹별 필드·Table/View | 값 편집 → 필터·정렬·열 설정 → 저장 후 복원 |
| B04 | Pipeline | 분류 필드 선택 → 카드 이동 → Table·상세의 값 일치 |

### G03 — 공통 계약과 DB 설계

- [ ] 기본 정보, 그룹 소속, 그룹별 값, View 설정의 소유 범위를 정한다.
- [ ] 테이블·컬럼·타입·null/default·FK·unique·CHECK·index와 삭제 정책을 명세한다. 단순 개념도를 구현 확정 스키마로 취급하지 않는다.
- [ ] CustomFieldValue 저장 방식, 관계 참조, 자동 저장·동시 수정·버전 충돌 처리 방식을 정한다.
- [ ] API별 이름·식별자·method/path·request/response 필드·validation·업무 흐름·권한·오류·연결 DB를 정한다.
- [ ] Workspace/Group/레코드 접근 검증과 트랜잭션 범위를 명시한다.
- [ ] 기존 Object/List/View/Attribute 및 FE route·API client·seed·fixture·테스트의 교체 대상을 연결한다.
- [ ] 기존 데이터 보존 여부, 이전 대상 환경, 구 ID→새 ID 매핑 필요성을 확인한다.

완료 기준: 해당 기능의 화면 행동을 API와 DB로 추적할 수 있다. 권한·삭제·저장 의미가 미확정이면 관련 구현을 시작하지 않고 확인 작업으로 남긴다. 미확인 외부 동작과 내부 구현 선택을 구분한다.

### G04 — DB·Backend 구현

- [ ] G03 계약에 맞는 schema/migration과 모듈 내부 구현을 작성한다.
- [ ] modular monolith와 Clean Architecture 기준을 지키고, 다른 모듈은 공개 application port로 접근한다.
- [ ] 입력 검증·접근 권한·참조 무결성·트랜잭션·오류 응답을 구현한다.
- [ ] 관련 typecheck/lint/test와 schema 변경 시 Prisma 검증을 수행한다.

완료 기준: 계약에 정한 저장·조회·권한 거부·실패 처리가 검증된다. 실행 대상 환경이 정해지지 않은 원격 DB에 migration을 적용하지 않는다.

### G05 — Frontend 연동

- [ ] API client·query key·route·화면 상태를 새 계약에 연결한다.
- [ ] 생성·편집·취소·자동 저장·실패 복구·충돌 표시를 확인된 UX대로 구현한다.
- [ ] Workspace와 사용자 변경 시 캐시가 섞이지 않도록 처리한다.
- [ ] 해당 기능의 mock을 실제 응답으로 교체하고 관련 typecheck/lint/build를 수행한다.

완료 기준: 실제 API를 통해 같은 흐름을 완료할 수 있다. 현재 명시적 save/undo 코드를 그대로 두고 자동 저장 구현이 끝났다고 표시하지 않는다.

### G06 — 통합 검증

- [ ] 등록·수정 값이 새로고침과 재접속 후 유지된다.
- [ ] 같은 사람을 두 그룹에서 보았을 때 기본 정보는 공유되고 그룹별 값은 분리된다.
- [ ] 다른 Workspace·권한 없는 Group의 데이터가 섞이거나 노출되지 않는다.
- [ ] Pipeline 이동 결과와 Table·상세의 값이 일치한다.
- [ ] 그룹에서 제거와 연락처 삭제가 각각 정한 범위대로 동작한다.
- [ ] 빈 상태·validation·API 실패·재시도·동시 수정이 처리된다.
- [ ] 기존 로그인·Workspace 접근·지원 접수에 회귀가 없는지 확인한다.

각 기능에 해당하는 항목을 검사하고, 적용하지 않는 항목은 이유를 기록한다. 완료 기준은 실행 결과와 화면 확인 근거를 남기는 것이다. 새 동작·데이터 경계에 필요한 테스트를 우선하며 불필요한 반복 검사는 피한다.

## 6. G07: 첫 흐름 이후 확대할 기능

아래는 최종 범위에서 제외한 기능이 아니라 후속 작업 목록이다. 각 항목을 독립된 조사·계약·구현·검증 단위로 나눈다. 권한처럼 첫 흐름에 필요한 부분은 G03~G06에서 먼저 구현한다.

- [ ] 가입·초대·Workspace 생성/전환·설정의 나머지 흐름.
- [ ] 연락처 검색·일괄 작업·중복 병합·이동·삭제/복구.
- [ ] Custom objects/Deals와 여러 사람·회사 연결.
- [ ] Notes·댓글·첨부·멘션 및 공개/비공개 범위.
- [ ] Tasks·담당자·기한·완료/재개·반복·알림 및 시간대.
- [ ] Workspace/Group 공유·멤버·역할별 권한의 전체 흐름.
- [ ] 가져오기·내보내기·필드 매핑·오류 결과·중복 처리.
- [ ] Interactions·메일/캘린더 동기화·연동 해제·재시도.
- [ ] Messages·캠페인·템플릿·후속 메일·예약/중지·결과.
- [ ] Dashboard·집계·차트·데이터 소스와 접근 권한.
- [ ] Enrichment·AI 기능·수정·크레딧·실패 처리.
- [ ] folkX·외부 연동·API·Webhook.
- [ ] 계정 설정·사용량·요금제·결제 화면. 실제 결제 사업 정책은 별도로 정한다.
- [ ] 각 흐름의 모바일·반응형·접근성 검증.

## 7. G08~G09: 기존 구조 제거와 전체 비교

### G08 — 데이터 이전 및 기존 코드·테이블 정리

- [ ] 해당 기존 모델이 대체 구현으로 완전히 연결되는지 확인한다.
- [ ] 실제 환경과 데이터 보존 요구에 맞춰 이전 또는 명시적으로 요청된 초기화 방식을 정한다.
- [ ] 보존 대상의 건수·값·관계·그룹별 필드·View 설정을 전후 비교한다.
- [ ] 구 API·DTO·port·repository·DI·FE client·route·cache·seed·fixture·테스트 참조를 제거한다.
- [ ] 사용하지 않는 테이블·enum만 새 migration으로 제거한다. 과거 migration 이력을 임의로 지우지 않는다.
- [ ] 배포 중 호환성과 rollback 또는 백업 복구 경로를 검증한다.

완료 기준: 보존 데이터와 새 흐름이 정상이며, 제거 대상에 대한 실행 경로가 남지 않는다. Object/List/View/Attribute를 이름만 보고 일괄 삭제하지 않는다. ViewWidget은 Dashboard 기능과, ViewWorkDependency는 실제 대응 기능 유무와 연결해 판단한다.

### G09 — 전체 비교

- [ ] 기능 대응표의 모든 항목에 조사·구현·검증 상태가 있다.
- [ ] 화면뿐 아니라 저장·권한·삭제·오류·모바일 동작까지 원본과 비교했다.
- [ ] 미확인·미구현·의도한 차이를 각각 기록하고 동등 구현으로 뭉뚱그리지 않았다.
- [ ] README·기획·UX·DB/API 문서가 실제 구현 상태를 설명한다.
