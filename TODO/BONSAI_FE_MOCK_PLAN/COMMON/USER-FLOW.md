# 전체 사용자 흐름

현재 동작·검증 갱신: [G16 문서 브랜드](../RESULTS/G16_RESULT.md) · [G01~G15 감사 후 재점검](../RESULTS/G01_G15_RECHECK_RESULT.md). 기존 원본/시각/환경 대기는 유지한다.

상태: FE 목 구현용 흐름 설계. 분기·권한·URL은 관찰 근거와 추가 분석 결과로 확정한다. 모든 사용자가 아래 기능을 순차 수행해야 한다는 뜻이 아니다.

## 로그인 전과 앱의 연결

G02~G09는 익명 세션에서 독립 실행한다. 메뉴와 CTA 목적지는 [공개 웹 명세](PUBLIC-WEB.md)에 기록한다. 아직 인증 화면을 만들기 전에는 route/intent 전달만 검증하며, G10~G14에서 실제 화면 간 왕복을 완료한다.

G14 완료 전에 `랜딩 → 가입 → 온보딩 → 앱`, `공개 페이지 → 로그인 → 의도한 목적지`, `템플릿·생성기 → 가입 → 초안 복귀`, `로그아웃 → 공개 화면`을 브라우저에서 검증한다. 원본 복귀 규칙이 미확인이면 R01/R02에 근거 또는 목 가정을 남긴다. 이메일·민감한 입력 전체를 URL에 싣지 않는다.

현재 코드의 경로를 유지해야 하는지 G00/G01에서 확인한다. 공개 `/`, `/pricing`, `/templates/:slug`, 인증 `/login`, `/signup`, 내부 `/app/...`, 외부 `/forms/:shareId`, `/book/:shareId` 등은 설명용 후보이며 확정 route나 현재 구현 목록이 아니다.

## 내부 업무 연결

회사·멤버 → 고객·연락처 → 프로젝트 → 작업·시간 → 청구서 → 입금·장부 → 대시보드가 같은 ID와 저장 결과로 이어져야 한다. 제안·계약·서비스·폼·예약은 해당 객체와 연결되는 별도 진입을 가진다. 각각 독립적으로 시작할 수 있는 조건은 추가 분석으로 확인한다.

거래 → 견적 → 합의 문서 → 프로젝트·작업 → 시간·비용 → 청구·부분 입금 → 고객 포털은 [제품 기능 대응표](../../../AGENT/PM_AGENT/PLANNING/BONSAI_FEATURE_PARITY_MATRIX.md)의 중심 검증 시나리오다. Gummble 캡처가 부족한 거래·견적 등은 R04를 거쳐 추가 명세를 배정한다. 모든 경로에 자동 전환을 강제하지 않는다.

| 연결 | 같은 데이터로 확인할 사항 | 잘못 합치지 않을 상태 |
| --- | --- | --- |
| 고객 ↔ 프로젝트 | 선택한 고객 ID, 프로젝트 목록·검색·문서 선택지 | 운영 회사·고객 회사·사용자 계정 |
| 프로젝트 ↔ 전체 작업 | 같은 작업 ID, 하위 작업·담당자·활동 | 동명 작업의 서로 다른 ID |
| 타이머 ↔ 시간 목록 | 시작/종료·시간대·초 단위·수동 입력 | 모달 닫기와 타이머 정지 |
| 시간 ↔ 청구서 | 미청구 시간 선택·금액·저장·중복 편입 방지 | Draft, Billed, Paid |
| 문서 ↔ 활동 | 작성·발송·수신자별 확인·서명·수락 | 내부 Accepted와 고객 동의, 작성자 Finalized와 양측 서명 |
| 예약 유형 ↔ 예약 내역 | 유형별 공개 URL·슬롯·예약 ID | 유형 생성과 실제 예약 확정 |
| 장부 ↔ 보고 | 금액·기간·통화·포함 기준 | 수기 수입과 결제 제공자의 실입금 |

## 공통 실패·재진입

정상 결과 외에 입력 오류, 취소, 저장 실패 후 재시도, 새로고침, 삭제/만료된 직접 링크, 권한 부족, 세션 만료, 빈 목록과 검색 무결과를 각 행동에 맞게 정의한다. 권한을 숨기는 UI와 실제 권한 집행은 별개이며 현재 계획은 목 역할 시나리오만 검증한다.

교차 화면 검증은 [G83](GOAL-SPECS/G83.md), 역할·접근성·전체 범위 판정은 [G84](GOAL-SPECS/G84.md)가 담당한다.

## G16 현재 구현 경로

가상 로그인 → `/app/settings/company` → Branding → `/app/settings/branding` → No image/Abstract/Plant·로컬 로고 미리보기 → Save → Account/Branding 재진입. 직접 보호 URL·뒤로/앞으로도 같은 저장값을 읽는다. Cancel save는 입력 유지, Discard/페이지 이탈은 입력 폐기다. 새로고침/새 탭은 기존 메모리 초기화 정책이다.

Desk·Custom Header·폰트/색·미관찰 크기·다른 White Label은 상태를 바꾸지 않는 로컬 안내까지만 제공한다. 새 문서 기본값 복사는 최소 목 시나리오이며 실제 문서 작성/발송/결제 연결은 후속 Goal 대기다. [결과와 수명](../RESULTS/G16_RESULT.md).

## G17 팀 관리의 현재 경로

Settings/계정 메뉴 Team → `/app/settings/team`, Invite Team → `?invite=1`. 기존 `/app/pending/team`은 목록으로 replace한다. 실제 보호 인증/온보딩 returnTo를 재사용하고 query는 모달 열림만 소유한다. 취소/성공은 query를 replace로 제거하며 뒤로/앞으로 재진입은 빈 초안이다. 저장 목록은 같은 workspace에 유지한다. Pending 행 메뉴→확인→정확한 ID 제거, 실패/재시도/취소와 동명이인 보존을 [G17 결과](../RESULTS/G17_RESULT.md)에 기록한다. G13 이메일 제안은 자동 편입하지 않으며 G18 수락/협업자 접근은 미착수다.

## G18 연결 갱신 (2026-11-22)

G17 Team preview controls → `/invite/:workspaceId/:invitationId` → 다른 이메일은 로그아웃, 새 계정은 초대 전용 입력, 기존 계정은 로그인 returnTo `/app/invitations/...` → 같은 Pending ID 수락 → 허용 프로젝트/작업. 과거 일반 가입의 다른 이메일을 하나의 성공 이력으로 합치지 않는다. [G18 결과](../RESULTS/G18_RESULT.md)·[R02 분석](../RESULTS/R02_RESULT.md). 미관찰 동작은 명시한 목 정책이며 서버/API/DB 확정이 아니다.

## G27 최종 연결 갱신

[G18~G27 결과](../RESULTS/G18_G27_RESULT.md): G18의 최소 프로젝트/작업은 G21~G27의 실제 로컬 공유 원본에 연결했다. 고객→프로젝트→전체/프로젝트 작업→하위/댓글→초대 협업자→소유자 재로그인을 같은 ID로 검증했다. 기존 표의 소유 범위는 유지하며 미수록 업무/실서비스 완료로 확대하지 않는다.

## 2026-11-22 G28 상태 정의·완료 연결

`/app/tasks` 및 프로젝트 Tasks의 같은 작업 ID → 상태 선택 → Settings → workspace 표시명/색/순서 변경. Done ID는 완료 의미를 유지하고 과거 활동명은 저장 당시 snapshot이다. Dashboard 작업 체크는 같은 TaskStore를 변경하며 완료 행/하위/댓글/기록 시간은 유지한다. 취소→To Do, owner 정의 편집, Enter/blur/색 즉시 저장·Done 마지막 고정은 목 정책이다. 추가/삭제와 실제 공유·권한은 미확인이다. 실패는 입력 유지, 닫기/이탈은 미저장·pending 폐기, 성공은 같은 탭에 유지, reload/Reset은 seed 초기화. [G28 결과](../RESULTS/G28_RESULT.md).

## 2026-11-22 G29 보관·삭제 연결

전체/프로젝트 카드 또는 같은 ID 패널 → Archive(목 즉시 요청) / Delete→Confirm Deletion→확정. 실패는 동일 대상 재시도, X/outside/Escape/pending 취소·이탈은 원본 유지, 성공 후 활성 소비/요약에서 제외하고 패널은 원래 이력으로 닫는다. 이후 앞으로/기록 링크는 unavailable, hard reload/Reset은 seed 초기화다. 보관은 내부원본 유지/완료와 별개, 삭제는 부모 원본만 제거하며 시간·금액은 보존한다. owner-only와 연관자료/수명은 목 정책이고 실제 cascade/복원/청구는 미확인이다. [G29 결과](../RESULTS/G29_RESULT.md).
