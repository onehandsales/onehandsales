# G32 — 전역·작업 타이머

상태: **미착수** · 영역: **내부 업무** · 이전 대화 번호: `G24`

## 1. 목적·포함·제외

- 목표: 팝오버 닫기·정지·재개·Done을 나누고 1시간+7초의 개별 기록과 총합을 확인한다.
- 행위자: 가상 workspace의 소유자·허용된 멤버. 역할별 가시성은 근거 또는 명시한 목 시나리오로 구분한다.
- 포함: 제목의 동작과 아래 원본 단계, 연결된 R Goal에서 이번 범위로 확정한 성공·취소·실패·재진입.
- 제외: 실제 인증/업무 API 연결, 실제 발송·결제·서명·은행 동기화, DB 변경, 배포. 원본에 없는 기능은 분석 결과와 연결한 별도 구현 Goal로 등록한다.

## 3. 화면·입력·근거

- 주요 입력·표시: 실행 시간, Project/Task, 날짜, Rate, 메모
- 페이지/feature UI는 표시·사용자 의도, hook은 상태·요청, adapter는 저장소 경계를 맡는다. 모든 신규 컴포넌트·hook·함수에 한 줄 한글 `// 기능 : ...` 책임 주석을 둔다.
- route·진입·복귀는 [전체 사용자 흐름](<../USER-FLOW.md>)을 기준으로 해당 Goal 착수 때 확정한다. 원본 URL과 우리 URL 후보를 구분한다.

## 4. 목 데이터·저장·검증 경계

- 가상 ID·고정 시각·통화·역할의 시작 seed를 기록한다. 동명 객체를 같은 ID로 합치지 않는다.
- 입력 초안과 저장 결과를 구분한다. 하위 Save/전체 Save/자동 반영은 출처에 맞춰 선택하고 취소·실패 시 남는 값을 명시한다.
- 같은 객체의 목록·상세·선택지·검색·집계를 하나의 저장소에 연결한다. 이미 구현된 소비 화면은 재조회하고 아직 없는 소비 화면은 후속 Goal의 연결 검증에 남긴다.
- 조회는 초기 로딩·빈 데이터·필터 무결과·오류·권한 제한, 변경은 pending·성공·검증 오류·실패·재시도를 해당 행동에 맞게 준비한다.
- 로컬 목: [화면 상태 기준](<../MOCK-UI-STATE.md>)에 따라 표시·입력·변경을 프론트 내부에서 처리한다. API 명세·HTTP adapter·DB 스키마는 작성하지 않는다.

## 5. 기능별 완료 체크

- [ ] [UX/UI 재현 기준](<../UXUI-REPLICATION.md>)에 따라 원본과 같은 viewport에서 폰트·크기·색상·간격·배치·플로우를 비교하고 남은 차이를 기록했다.

- [ ] 팝오버 닫기·정지·재개·Done을 나누고 1시간+7초의 개별 기록과 총합을 확인한다.
- [ ] 실행·일시정지·재개·Done과 팝오버 닫기를 나눈다. 경과 시간은 제어 가능한 시계로 관리하고 페이지 이동 시 중복 타이머를 만들지 않는다.
- [ ] 실행 시간과 기존 기록 합계를 나눈다. 7초·1시간 두 행을 유지하고 정지·완료·재개·화면 이동 정책을 전역 타이머와 맞춘다.
- [ ] 정상·오류 수정 후 재시도·취소·재진입 결과와 관련 화면의 같은 ID를 확인했다.
- [ ] 직접 URL·뒤로/앞으로·키보드·모달 포커스·좁은 화면을 확인했다. 관련 없는 항목은 이유를 적었다.
- [ ] 실제 인증·업무·외부 서비스 호출 없이 목으로 동작함을 네트워크에서 확인했다.
- [ ] 변경에 맞는 typecheck/lint/상태·계산 검증/브라우저 시나리오를 실행하고 실제 결과를 기록했다.
- [ ] 원본과의 차이·남은 질문·새 데이터 요구·후속 Goal을 결과 기록에 연결했다.

## 6. 이번 기능에서 잊지 말아야 할 질문

원본 질문을 보존한 목록이다. 화면·사용자 동작은 이번 FE 범위에서 확인하고, API·DB·서버 정책·실계정 동작은 후속 메모로 남긴다. 후자의 답을 확정하는 것은 이 Goal의 착수·완료 조건이 아니다.

- [ ] 프로젝트 없이 Done이 가능한가? 검증 환경에서 빈 값 제출로 확인하고 필수 관계를 결정한다.
- [ ] 시간은 서버시각·클라이언트시각 중 무엇을 기준으로 계산하는가? 새로고침·다중 탭·시간대 전환을 재현한다.
- [ ] 프로젝트 변경 시 요율20이 어디서 유래하는가? 프로젝트·사용자·작업 기본 요율을 각각 바꿔 확인한다.
- [ ] 완료·삭제·재개 시 기존 기록이 수정되는가? 네트워크와 목록 ID를 비교하고 이력·중복 방지 후보를 결정한다.
- [ ] 단계 01: 날짜와 집계의 기준 시간대, 그래프 산식, 타임라인 아이콘의 정확한 날짜 의미, 역할별 접근 권한, 홍보 노출 조건은 이 이미지로 확인할 수 없다.
- [ ] 단계 02: 조회 기간·내 시간/팀 시간 범위와 배경 데이터 변경 이유.
- [ ] 단계 03: 프로젝트 없이 완료할 수 있는지, 최초 레코드 생성 시점, 삭제 확인 과정.
- [ ] 단계 04: 권한별 노출·완료 프로젝트 포함·검색 기능.
- [ ] 단계 05: 20이 프로젝트 기본값인지 사용자 설정인지, 자동 저장 요청·실패·debounce 동작.
- [ ] 단계 06: 미입력·0의 구분 및 청구 시 요율 결정 방식.
- [ ] 단계 07: 메모 저장 시점, 줄바꿈·길이 제한, Task 신규 생성 결과.
- [ ] 단계 08: 페이지 이동·새로고침·브라우저 종료 후 연속성, 다른 기기 동기화.
- [ ] 단계 09: 일시정지와 최종 제출의 서버 상태 차이, 재개 구간 누적·동시 타이머 제한.
- [ ] 단계 10: 실제 영속 저장·새로고침 후 유지, 청구 상태·표시 목록 기간.
- [ ] 타이머 일시정지만으로7초 행이 생성되는가? 시작→정지→Done을 각각 재현한다.
- [ ] 브라우저 이동·새로고침·다른 작업의 타이머 시작은 이전 세션에 어떤 영향을 주는가? 전역 타이머와 대조한다.
- [ ] 7초 기록의 요율·청구 상태·멤버·업무일자는 어디서 상속되는가? 기록 상세/API로 확인한다.
- [ ] 단계 01: 동일 제목 작업 구분·시간 상세·소유자.
- [ ] 단계 02: 재생 시 기존기록 재개인지 새 기록 생성인지.
- [ ] 단계 03: 상단 전역타이머 동기화·서버실행상태.
- [ ] 단계 04: 백그라운드 실행·서버 기준시각·표시갱신주기.
- [ ] 단계 05: 두 같은 제목 카드의ID·어떤 작업이 시간기록 보유인지.

질문의 체크는 근거·선택·미해결 처리 위치를 남겼다는 뜻이다. 모든 Bonsai 동작을 검증했다는 뜻은 아니다. 관련 R Goal의 결과와 충돌하면 구현 전에 정리한다.
