## 1. 검토 결론

기존 `/sorts`와 `/settings` 재사용은 현재 코드와 맞는다. 원본 조회와 대시보드 저장은 필요한 모델이 있으나 실행 계약까지 완성되어 있지 않다. 저장 구조의 존재, 메뉴 조회 가능, 실제 값의 실행 가능, 저장 가능은 각각 별도 사실이다.

| 검토 항목 | 현재 사실 | 후속 구현 시 판단 |
| --- | --- | --- |
| View Type | 11종 Enum 존재 | 버튼 노출과 신규 기능 지원 범위를 구분 |
| Object/List 소속 | View의 두 FK 모두 nullable, 기본 ID FK | 실행 대상 해석을 정하고 임의 XOR를 추가하지 않음 |
| 필터 | 그룹·조건·AND/OR·ANY/ALL·문자열 연산자 저장 | 타입별 연산·빈 값·여러 루트의 평가 규격 필요 |
| 참조 경로 | 순서 있는 JSON UUID 배열 | 관계의 각 단계와 최종 속성 도달 가능성 검증 필요 |
| 정렬 | 방향·우선순위·추가 JSON 저장 | 실제 값 비교와 페이지 처리 필요 |
| 집계 | MEASURE, GROUP/SERIES, PIVOT_ROW/PIVOT_COLUMN 연결 | 집계 함수·그룹 키·중복·소계 규격 필요 |
| 위젯 | 원본 View 참조·배치·제목·숨김 저장 | 수정 권한·배치·순환·동시성·재요청 규격 필요 |

## 2. 스키마와 실행 기준

### 2.1. 행 기준과 속성 시작점

| View의 조회 대상 | 결과 행의 식별자 | sourceScope | 값을 읽는 위치 |
| --- | --- | --- | --- |
| Object | Record ID | RECORD | 해당 Record 값 또는 그 참조 경로 |
| List | ListEntry ID | LIST_ENTRY | 해당 Entry의 List 업무값 또는 그 참조 경로 |
| List | ListEntry ID | RECORD | 해당 Entry가 연결한 Record 값 또는 그 참조 경로 |

List View에서 `sourceScope=RECORD`라고 결과 행 단위를 Record로 바꾸지 않는다.

```text
Entry 1 → Record A → List 업무 금액 500만원
Entry 2 → Record A → List 업무 금액 200만원

List 원본: Entry 1, Entry 2 두 행
Record A라는 이유로 한 행으로 합치지 않음
```

같은 List/Record 조합을 유일하게 만드는 제약은 현재 없다. 이 문서는 반복 참여를 신규 생성 정책으로 확정하는 것도 아니며, 이미 존재하는 서로 다른 Entry를 조회 중 임의 병합하지 않는 기준이다.

관계값 연결로 한 Entry가 여러 DB 결과 행으로 늘어나는 현상은 다른 문제다. 필터의 존재 판정, 원본 행 페이지 처리, 집계 기여도를 구분해 JOIN 증식으로 건수·금액이 증가하지 않게 한다. 다중 그룹에 실제로 기여하는 규칙은 D05에서 결정한다.

### 2.2. 대상·참조 경로

- List에는 단일 기준 Object FK가 없다. 첫 Entry나 화면 이름으로 Object를 추정하지 않는다.
- 같은 Workspace의 속성이라는 이유만으로 현재 Object/List에서 읽을 수 있다고 판단하지 않는다.
- 직접 속성은 원본 Object/List와의 연결, 경로 속성은 출발점·RecordReference 타입·각 단계의 도착 대상·최종 속성을 검증해야 한다.
- RecordReference가 여러 Record로 이어질 때 조건들을 같은 대상 Record에 적용할지, 각각 다른 대상에 매칭해도 되는지 결정한다.
- 혼합 Object List에서 특정 속성이 없는 경우와 속성값이 null인 경우를 자동으로 동일하게 취급하지 않는다.
- View의 Object/List ID가 모두 있거나 모두 없을 때의 실행 방식은 D01에서 결정한다. 현재 메뉴 GET은 이를 임의 금지하지 않는다.

### 2.3. 필터·집계·원본의 일치

원본 조회와 차트/피벗은 동일한 대상, 유효 설정, 경로 해석, 연산 규칙을 공유해야 한다.

```text
저장 설정 또는 명시적인 화면 초안
→ 실행 가능한 조건·속성·그룹·집계 정의
→ Record/ListEntry 기준 대상 집합
→ 집계 결과 / 선택 구간의 원본 목록
```

일치 조건:

- 지원 연산자 목록과 속성별 비교값 형태를 정한다. 저장된 미지원 연산자를 무시해 조회 범위를 넓히지 않는다.
- 여러 필터 루트, 빈 AND/OR 그룹, ANY/ALL의 빈 값 집합, 존재하지 않는 참조를 정의한다.
- SUM/AVG/COUNT의 집계 단위와 null·0·값 없음, 다중 Measure의 처리 방식을 정한다. COUNT 때문에 가짜 Attribute를 자동 생성하지 않는다.
- 소계/전체 합계를 하위 셀의 단순 합으로 계산해도 되는지 검토한다. 다중 그룹·중복 제거 집계에서는 달라질 수 있다.
- 숨김·접힘은 표현 설정이다. 그룹 숨김을 데이터 제외 조건으로 해석할지는 명시적으로 결정한다.
- 날짜 구간 경계, Date와 Timestamp, timezone, Decimal 정밀도와 통화를 일치시킨다. 통화 변환 기능을 자동 도입하지 않는다.

### 2.4. 선택 구간과 조회 시점

| 클릭 위치 | 적용할 구간 |
| --- | --- |
| 헤더 원본 데이터 | View의 전체 대상, 전체/기여 행 구분은 D05 |
| 차트 막대 | 해당 그룹과 필요한 계열 |
| 피벗 일반 셀 | 해당 행과 열 |
| 피벗 행 합계 | 해당 행, 열 전체 |
| 피벗 열 합계 | 해당 열, 행 전체 |
| 피벗 전체 합계 | 전체 집계 대상 |

표시 문자열을 신뢰해 구간을 복원하지 않는다. 그룹 정의 ID·옵션 ID·타입별 값·날짜 경계 등을 검증하거나 서버가 발급한 검증 가능한 구간 토큰을 사용한다. 어느 방식을 사용할지는 D06에서 확정한다. 토큰이 있더라도 접근 권한을 다시 검사한다.

빈 값 그룹 선택과 조건을 생략한 전체 선택은 구분한다. 현재 집계에 없는 임의 속성이나 타 Workspace 구간을 요청할 수 없도록 한다.

같은 실행기를 쓴다는 사실만으로 서로 다른 요청 시점의 데이터까지 같아지지 않는다. 차트 조회 이후 원본이 수정되면 합계가 달라질 수 있다. 현재 데이터 재조회인지 동일 시점 조회인지 D07에서 정한다. 단순 조회 시각 필드나 설정 버전만으로 업무 데이터 스냅샷이 보장된다고 설명하지 않는다.

현재 메뉴 GET 자체도 여러 SELECT 사이의 단일 시점 스냅샷을 보장하지 않는다.

### 2.5. MAP 정렬

- 정렬 규칙 배열은 `sortOrder, createdAt, id` 순서다. 실제 행은 각 규칙의 `sortDirection`에 따라 비교한다.
- 숫자를 문자열 순서로 비교하지 않는다. 날짜·시각·옵션·참조·다중값 비교 기준을 D04에서 정한다.
- 더미 `configJson.nulls=LAST`는 저장 예시다. 모든 값의 기본 null 순서와 다중값 정렬 규격이 확정된 것은 아니다.
- 필터와 전체 정렬 이후 페이지를 나눈다. 한 페이지만 가져와 FE에서 정렬하는 방식으로 전체 순서를 보장하지 않는다.
- 동률을 해소하는 행 ID, 커서에 필요한 정렬값, 조건 변경 시 커서 무효화를 정의한다. 조회 중 값이 변경되는 경우의 일관성도 D07에 포함한다.
- 핀은 지리적 위치를 유지한다. 좌표 없는 기록을 목록에서 자동 제외하지 않는다.

### 2.6. 대시보드

- 대시보드의 Object/List 소속은 모든 위젯의 데이터 범위를 자동 제한하는 조건이 아니다. 각 위젯은 원본 View 기준을 따른다.
- 동일 원본 View를 여러 위젯에서 사용해도 각 위젯 ID·제목·배치·숨김을 보존한다.
- 현재 설정 GET은 직접 원본 요약만 조회한다. 위젯 결과, 재귀 실행, 중첩 허용 판정을 대신하지 않는다.
- 편집 초안에는 숨긴 위젯도 포함한다. 화면에 안 보인다는 이유만으로 저장 요청에서 제거하지 않는다.
- 후보 조회 결과는 저장 시점까지 유효하다는 보장이 없다. 저장 시 원본 존재·소속·지원 정책을 다시 검사한다.
- 자기/순환 참조를 금지하는 정책을 채택하면 동시 요청 A→B, B→A도 검토한다. 각각의 선행 조회와 단순 트랜잭션만으로 순환 방지를 보장하지 않는다.
- 위젯 제거는 해당 배치 행 제거다. 원본 View/Record/ListEntry 삭제로 연결하지 않는다.

## 3. 선행 결정 항목

모든 항목은 미확정이다. 다음 표는 결정할 질문과 필요한 산출물을 적은 것이며 특정 정책 채택을 뜻하지 않는다.

| ID | 결정할 질문 | 확정 시 남길 결과 | 영향 |
| --- | --- | --- | --- |
| D01 | Object/List 연결 0개·2개, 혼합 Object List를 어떻게 실행하는가? | 원본 판정표, 적용 불가 속성과 null 구분 | 원본/집계/지도 |
| D02 | 참조 경로의 다중 대상과 조건 간 대상 일치를 어떻게 평가하는가? | 경로 타입·깊이·비교 결합 규격과 예제 | 공통 실행기 |
| D03 | 지원 연산자·여러 루트·빈 그룹·ANY/ALL의 빈 집합 규칙은? | 타입별 연산자/비교값·진리표·미지원 오류 | 필터 실행 |
| D04 | 다중값·옵션·참조·null의 정렬 기준은? | 비교 함수, 기본 순서, 동률·커서 규격 | MAP/원본 목록 |
| D05 | 집계 기여 행, COUNT 단위, null·중복·소계·숨긴 그룹은? | 집계별 기여 규칙, 예상 합계/건수 예제 | CHART/PIVOT |
| D06 | 구간 선택을 어떤 요청 구조로 표현하는가? | 검증 가능한 구간 DTO/토큰, 합계·빈 그룹 구분 | 원본 조회 |
| D07 | 현재값 재조회와 동일 시점 중 무엇을 보장하는가? | 읽기 일관성·설정 변경·데이터 변경·커서 수명 | 조회 전체 |
| D08 | 미저장 초안을 실제 조회에 반영하는가? | saved/draft 구분, preview 필요 여부·요청/캐시 규격 | FE/실행기 |
| D09 | 원본 목록에 어떤 열·표시명을 제공하는가? | 열 선택·참조 경로·옵션/Actor/Record 표시명 DTO | 원본 응답 |
| D10 | 위젯 후보 범위와 중첩 DASHBOARD를 어디까지 허용하는가? | 기존 목록 재사용 여부·타입/순환 정책·범위 검증 | 후보/저장/실행 |
| D11 | 위젯 배치와 표현 JSON의 규격은? | 키·타입·범위·반응형·누락/null·미지원 키 처리 | 편집/저장 |
| D12 | 저장 권한·Actor·수정 대상은? | 읽기/쓰기 권한, field allow-list, 생략/null/삭제 의미 | 저장 |
| D13 | 동시 편집과 재요청을 어떻게 처리하는가? | 버전/잠금·경합·멱등 키/ID·응답 재사용 규격 | 저장 |
| D14 | 경로·오류·페이지 크기·성능 기준은? | 최종 DTO/route/status, 조회 제한·인덱스 계획 | 신규 API 전체 |

모든 신규 기능이 모든 항목의 결정을 기다려야 한다는 뜻은 아니다. 예를 들어 기존 `/sorts` 소비는 실행기 D01~D09 결정 없이 유지할 수 있고, 원본 조회의 계약 확정에 대시보드 D10~D13을 묶지 않는다.

## 4. 저장 로직의 추가 검토

| 위험 | 필요한 계약 |
| --- | --- |
| 멤버십이 있다는 이유로 임의 쓰기 허용 | D12의 수정 권한 판정. 현재 조회 Port에 역할별 권한이 있다고 가정하지 않음 |
| 배치 저장이 필터·정렬까지 초기화 | 변경 필드 범위를 명시하고 보내지 않은 설정 보존 |
| 일부만 로드한 위젯 배열로 전체 교체 | 전체 집합/부분 변경/명시 삭제 중 의미 확정, 숨긴 위젯 보존 |
| 동시에 저장해 먼저 저장된 결과 유실 | 버전 또는 잠금과 충돌 응답 정의 |
| 자식 변경이 부모 updatedAt에 자동 반영된다고 가정 | 모든 변경 경로를 포함하는 명시적인 변경 감지 규격 |
| 응답 유실 후 신규 위젯 중복 생성 | 논리 요청/위젯 식별과 중복 요청 응답 규격 |
| 저장 성공 후 추가 GET 실패를 저장 실패로 표시 | 저장 결과 응답과 후속 재조회 실패 구분 |
| 후보 확인 후 원본 삭제/순환 발생 | 트랜잭션 내 필요한 재검증·동시성 전략 |

설정 GET에는 현재 버전 필드가 없다. 샘플 JSON에 임의 `version` 키를 추가하지 않는다. 필요한 동시성 장치를 정한 뒤 API/DB 변경 필요성을 검토한다.

| G01 | 원본/주 화면이 공유할 조회 단위·필터·참조 실행 | 모든 타입 렌더러·저장 | 반례·소속 격리·다중값 테스트와 Port 경계 확인 |
| G02 | 원본 조회와 집계 구간 연결 | Record 값 수정 | 집계/원본의 의미 일치, 페이지·오류 검증 |
| G03 | MAP 정렬 설정 재사용과 주 화면 정렬 연결 | 거리/경로 최적화 | 전체 정렬 후 페이지 처리, 좌표 없는 기록 보존 |
| G04 | DASHBOARD 편집 초안과 필요한 후보 조회 | 구성 저장 | 기존 UX 보존, 후보 소속·상태·취소 검증 |
| G05 | 별도 확정된 구성 저장 | 원본 View/업무값 수정 | 원자성·경합·재요청·삭제 범위 검증 |
| G99 | 비즈니스 로직·컨벤션·주석·FE/BE 계약 검토 | 미검증 배포 완료 주장 | 실제 실행한 검증과 남은 한계를 기록 |

원본 집계 주 화면이 별도 계획으로 진행되면 G01/G02의 공통 실행기를 중복 구현하지 않고 책임과 선행 관계를 연결한다.
