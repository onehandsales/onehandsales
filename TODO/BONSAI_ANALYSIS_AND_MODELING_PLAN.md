# Bonsai 전체 화면·업무 흐름 분석과 데이터 모델링 계획

Updated: 2026-11-17

Status: 진행 순서 합의 / 자료 접근·초기 확인 완료 / 전수 분석·모델링 미완료

## 1. 목적과 진행 원칙

Bonsai의 전체 기능·UX를 재현하기 위해 **플로우로 전체 업무 지도를 만들고, 모든 화면·UI 요소를 공식 도움말·API와 대조한 뒤 전체 데이터 모델을 설계한다.** 플로우 우선은 분석 순서이며, 전체 화면 검토 범위를 줄이는 기준이 아니다. 근거·차이·미확인을 기록하고, 전체 재현 이후 차별화한다.

이 계획은 사용자와 합의한 조사·설계 순서를 한 문서로 관리한다. 이번 문서 작성은 전수 분석이나 FE·BE 구현, 실제 DB 변경을 완료했다는 뜻이 아니다.

| 공식 도움말·API | 이전 조사에서 주요 도움말과 API 개요 확인 | 전체 기능·관련 문서·endpoint·모델 목록을 기준으로 상세 대조와 누락 점검 |
| 실제 계정 | 직접 동작 검증 미수행 | 문서·화면 간 불일치, 저장·권한·상태 변화 등 필요한 재현 |

`Latest` 표시는 최신 실서비스와의 일치를 보장하지 않는다. 42개 flow가 642개 화면 전부를 포함하는지, UI Elements 75개가 Screens와 중복되는지는 조사 후 판정한다. 세 개수를 독립 기능 수로 합산하지 않는다.

## 3. 실행 순서

| 단계 | 수행할 작업 | 산출물·완료 기준 |
| --- | --- | --- |
| 1. 전체 목록 고정 | flow 42개, 해당 버전의 screen 642개, 로컬 UI 이미지 75개를 ID·출처로 목록화한다. 페이지네이션·응답 잘림을 확인한다. | 기준일·버전·총수·고유 ID 수·누락·중복을 확인한 검토 목록. 새 자료가 발견되면 변경 이력을 남기고 범위를 확장 |
| 2. 플로우 지도 | 42개 flow를 업무 기능, 계정·설정, 공개 사이트 등으로 분류한다. 시작·종료 화면, 단계 순서, 하위 flow, 다른 업무와의 연결을 조사한다. | flow별 목적·단계·화면 ID 대응표. 목록 조회와 실제 흐름 분석 상태를 구분 |
| 3. 화면·UI 요소 분석 | flow의 순서대로 원본 이미지를 열어 입력·버튼·문구·목록·상세·모달·상태 차이를 기록한다. 관련 UI Elements를 함께 보고 나머지도 별도로 검토한다. | 화면별 관찰 기록과 UI 요소 연결. 비슷한 이미지도 차이를 확인하며, URL 수집·OCR만으로 이미지 검토 완료 처리하지 않음 |
| 4. 공식 근거 대조 | 3단계와 기능별로 병행한다. 공식 도움말의 업무 규칙과 API의 필드·참조·입출력·상태·오류를 대조한다. 버전·요금제·권한·국가 조건과 실제 계정 확인 필요 사항을 기록한다. | `화면 → 행동 → 데이터·상태·권한 → 공식 근거 → 모델 후보` 대응표. API에 없는 제품 기능도 범위에 포함 |
| 5. 누락·교차 검토 | 전체 screen ID와 flow에서 검토한 ID를 대조한다. flow에 없는 화면, UI 이미지 75개, 하위 flow, 관련 공식 문서의 미검토 항목을 보완한다. | 전체 자료의 검토 이력과 남은 질문. 고객 변경·견적 수정·문서 확정·청구·입금 등 기능 간 영향 재검토 |
| 6. 전체 데이터 모델링 | 전체 업무의 개념·관계·상태를 정리하고 엔티티·필드·관계 개수·제약·이력·권한을 설계한다. 현재 schema·API·FE 의존과 대조한다. | 전체 관계도, 모델·필드 정의, 상태·권한 표, 근거·가정·미확인 목록, 기존 모델 유지·변경·교체 및 데이터 이전안 |
| 7. 기능별 구현 | 전체 조사와 모델 초안을 바탕으로 기능별 상세 DB·API 계약과 FE 화면을 구체화하고 실제 저장·조회까지 연결한다. | 원본 비교, 재조회·오류·권한·관계 검증. 기능별 이전을 검증한 뒤 사용하지 않는 기존 참조 정리 |

핵심 업무부터 상세 검토하되 42개 flow와 전체 자료를 모두 다룬다. 3~4단계에서 발견한 새로운 화면·문서는 목록에 추가한다. 화면 mock과 설계 후보는 조사 중 작성할 수 있으며, 최종 스키마·구현 완료와 구분한다. Figma 제작은 필수 선행 단계가 아니다.

## 4. 화면별 기록과 진행률

각 검토 기록에는 아래 항목을 남긴다. 한 화면이 여러 flow에 등장하면 이미지 기록은 공유하되 flow별 맥락·전후 상태는 각각 기록한다.

| 구분 | 필수 기록 |
| --- | --- |
| 식별·조건 | screen/flow ID, flow 내 순서, UI 이미지 경로, 원본 링크, 조회일, 버전·캡처일·viewport, 계정 조건. 알 수 없는 값은 미확인 |
| 관찰 | 화면 목적·배치·문구, 입력·필수 표시·기본값, 버튼·탭·메뉴, 보이는 정상·빈·로딩·오류·권한·취소 상태 |
| 흐름 | 진입·종료 지점, 입력 전후·저장 후 차이, 재진입·복구. 정지 이미지로 확인할 수 없는 동작은 추정으로 표시 |
| 근거·설계 | 공식 문서 URL·절 또는 API endpoint/필드, 데이터 생성·변경·연결·공개 범위, 모델링 영향, 불일치·질문 |
| 검토 이력 | 이미지 검토 여부·일자, 문서 대조 여부, 재검토 필요 여부와 사유. 화면 관찰 / 공식 문서 확인 / 계정 재현 / 설계 가정 / 미확인을 구분 |

진행률은 **목록 확보 수, 실제 이미지 검토 수, 문서 대조 수, 재검토 대기 수**를 따로 보고한다. 화면 642개·UI 이미지 75개·flow 42개의 분모를 각각 유지하며, 겹치는 ID와 추가 발견 자료를 별도로 설명한다. 실제로 수행한 기록이 없는 항목은 완료로 집계하지 않는다.

## 5. 모델링·구현에 반영할 기준

- 공식 도움말은 업무 규칙, API는 공개 계약, Gummble은 화면·흐름, 실제 계정은 동작 재현의 근거다. 화면이나 API 응답을 비공개 DB 구조로 단정하지 않고 **동일한 기능을 지원하는 우리 모델**을 설계한다.
- 고객·담당자·거래·견적·문서·프로젝트·작업·시간·청구·입금을 구분한다. 관계 개수·필수 입력·삭제 정책은 근거 없이 확정하지 않는다. 문서 snapshot, 금액·통화·반올림, 날짜·시간대, 상태 전이·중복 처리·권한 경계를 검토한다.
- 인증·사용자·Workspace의 재사용 가능성을 검토하고, 기존 Object/Attribute/Record/List/View는 기능 요구와 실제 의존에 따라 처리한다. 사용자 정의 필드·보기 설정도 필요한 확장 기능으로 검토한다.
- Backend는 modular monolith와 Clean Architecture, 모듈 공개 port, application 소유 transaction 기준을 유지한다. FE는 `FE/user-web`을 중심으로 feature·API client·캐시 경계를 설계하고, 고객 포털과 운영자 Admin을 구분한다.
- 실제 연동 전에 기능별 API 계약에 요청·응답·오류, 인증·권한, DB 연결, transaction·rollback, idempotency/outbox, 로그·민감정보 처리, FE 갱신 범위를 정한다. 계약은 구현 전에 확정한다.
- 현재 계획은 조사·설계 순서다. 실제 DB 초기화·삭제·migration 실행을 포함하지 않는다. 후속 구현에서는 데이터 보존·이전·복구와 FE/API 전환을 함께 검증한다.

## 6. 조사·설계 완료 기준과 첫 작업

- [ ] 기준 목록과 추가 발견 자료를 포함해 모든 화면·UI 이미지의 실제 검토 기록이 있다. 미조회·조회 실패 항목은 완료로 처리하지 않았다.
- [ ] 42개 flow와 발견된 하위 흐름의 단계·화면 연결을 검토했고, flow 미포함 화면도 확인했다.
- [ ] 공식 도움말·API를 조사 목록에 따라 대조했고, 기능 대응표에 버전 차이·누락·실계정 확인 필요 사항의 처리 상태를 기록했다.
- [ ] 모든 모델링 결정에 근거 또는 명시적인 설계 가정이 연결된다. 관계·상태·권한에 영향을 주는 미해결 질문을 확정 스키마에 숨기지 않았다.
- [ ] 전체 모델과 기존 DB/API/FE 전환안을 재검토하고, 기능별 상세 설계·구현 순서를 정했다.

**첫 실행 작업:** 42개 flow의 전체 목록을 다시 확인하고, 버전 `2146`의 화면 ID 목록과 로컬 UI 이미지 75개의 파일명·ID를 수집해 대응표를 만든다. 이 단계의 완료는 자료 목록과 연결·미연결 상태를 설명할 수 있는 것이며, 이미지 분석이나 데이터 모델링 완료를 뜻하지 않는다.
