# 웹 브라우저·접근성·레이아웃 규칙

User Web과 Admin Web에 적용한다. 데스크톱 브라우저를 기준으로 업무 밀도를 설계하고 모바일 브라우저에서도 기능을 사용할 수 있게 검증한다. 네이티브 앱의 제스처·navigation stack을 웹 규칙으로 그대로 적용하지 않는다.

## 1. 주소와 브라우저 기본 동작

- 이동은 실제 URL을 가진 링크로 표현하여 새 탭 열기·주소 복사·브라우저 뒤로가기를 지원한다. 동작 실행은 button을 사용한다.
- 상세·탭·검색 등 복원할 상태는 [상태 소유권](../ARCHITECTURE/STATE_AND_DATA.md)에 따라 URL에 둔다.
- 주소 직접 진입, 새로고침, 뒤로가기·앞으로가기, 잘못된 ID를 확인한다. 이전 화면의 메모리 state가 있어야만 상세가 열리는 구조를 피한다.
- 페이지 제목과 주요 heading을 제공한다. route 변경 시 스크롤·포커스 복원 정책을 정하고 키보드 사용자가 위치를 잃지 않도록 한다.
- IME 조합 중 Enter를 제출·검색 완료로 처리하지 않는다. 앱 단축키는 입력 요소·브라우저 기본 단축키와 충돌하지 않게 한다.
- 새 창·클립보드·다운로드·파일 선택은 브라우저 제약과 실패 결과를 처리한다. 성공을 고정 토스트로 가정하지 않는다.

## 2. 시맨틱 HTML과 키보드

- `button`, `a`, `input`, `label`, `form`, `table` 등 목적에 맞는 HTML을 우선한다. 클릭 가능한 div로 기본 동작을 다시 구현하지 않는다.
- 폼 내부 일반 버튼에는 `type="button"`을 지정한다. 중첩 링크·중첩 버튼을 만들지 않는다.
- 입력은 보이는 label과 연결하고 도움말·오류를 `aria-describedby` 등으로 연결한다. placeholder를 유일한 이름으로 쓰지 않는다.
- 아이콘 버튼에 접근 가능한 이름을 제공한다. 색상·hover·tooltip만으로 의미나 필수 동작을 전달하지 않는다.
- Tab 순서가 시각적·논리적 순서와 맞도록 DOM을 구성하고 focus 표시를 유지한다. 양수 tabindex로 순서를 보정하지 않는다.
- 일반 데이터 표는 header 관계를 제공한다. spreadsheet 수준의 키보드 조작을 구현하지 않은 표에 `role="grid"`를 붙이지 않는다.
- 오류·상태 갱신은 필요 시 live region으로 알린다. 매 렌더링마다 반복 안내하거나 모든 텍스트에 ARIA를 덧붙이지 않는다.
- 드래그로만 가능한 정렬·이동에는 키보드 또는 메뉴 대안을 제공한다.

## 3. Dialog와 팝오버

모달은 열릴 때 내부의 적절한 요소로 초점을 이동하고, Tab 순환을 내부에 유지하며, 배경 조작을 막는다. Esc와 닫기 버튼을 제공하고 닫힌 후 trigger 또는 논리적인 다음 위치로 초점을 돌린다. 제목과 접근 가능한 이름도 연결한다. 파괴적 행동의 초기 초점은 실수로 확인하지 않도록 설계한다. [WAI-ARIA 모달 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

- 실제 모달 동작 없이 `aria-modal="true"`만 추가하지 않는다.
- 비모달 팝오버에 모달 focus trap을 무조건 적용하지 않는다. 메뉴·combobox·tooltip은 각 상호작용에 맞게 구현한다.
- 검증된 primitive가 설치되어 있는지 먼저 확인한다. 현재 `@radix-ui/react-slot` 설치가 Dialog primitive 설치를 뜻하지 않는다.
- portal 위치, stacking context, 스크롤 잠금, nested overlay의 닫힘 순서를 한곳에서 관리한다.
- 제출 중 닫힘 정책과 입력 손실 여부는 기능별로 명시한다. 비동기 결과가 닫힌 팝업을 다시 열지 않게 한다.

## 4. 반응형과 스크롤

- Bonsai 캡처의 viewport를 기록하고 같은 크기로 비교한다. 캡처 크기·이미지 픽셀·CSS px·DPR을 혼동하지 않는다.
- 화면 분기는 콘텐츠가 깨지는 지점에 맞춘다. 기기 이름에 의존해 고정 width를 쌓지 않는다.
- 기본 검토 폭은 360/390, 768, 1024, 1440 CSS px이고 넓은 화면은 1920도 확인한다. 이는 점검 표본이며 제품 breakpoint의 고정 목록이 아니다.
- 브라우저 확대와 긴 한글·영문·빈 값·큰 숫자에서 내용과 버튼이 잘리지 않는지 확인한다.
- 일반 세로 콘텐츠는 320 CSS px 상당의 폭에서도 정보 손실 없이 재배치되도록 검토한다. 의미상 2차원 배치가 필요한 표 등은 별도 영역의 스크롤을 검토한다. 이 점검만으로 WCAG 전체 준수를 선언하지 않는다. [WCAG Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- 페이지·패널·테이블 중 스크롤 소유자를 명확히 한다. 이중 세로 스크롤과 sticky header의 가림을 확인한다.
- Flex/Grid 자식의 `min-width: 0`, 최소·최대 폭, overflow 정책을 명시한다. 콘텐츠가 길다는 이유로 페이지 전체를 가로 스크롤시키지 않는다.
- 작은 화면에서 열을 숨길 때 같은 정보에 접근할 경로를 제공한다. 좁은 화면용 구성은 데스크톱 기능의 단순 제거로 해결하지 않는다.
- 터치·키보드에서도 핵심 버튼에 접근할 수 있어야 한다. 모바일 viewport 단위·소프트 키보드·safe area는 해당 UI에서 필요할 때 확인한다.

## 5. 스타일과 자산

- Bonsai 재현에서는 원본의 폰트·크기·색상·간격·radius·shadow·layer를 기준으로 token을 정한다. 기존 token은 원본과 맞을 때 재사용하며, 기존 스타일을 유지하려고 원본을 바꾸지 않는다. 반복 값은 의미 있는 token으로 관리한다.
- 버튼·입력·오버레이의 상태 스타일은 공통 컴포넌트에서 관리한다. selector로 다른 feature의 내부 DOM을 덮어쓰지 않는다.
- 캡처 재현에 필요한 치수는 근거를 기록한다. 모든 길이를 임의의 반응형 수치로 바꾸거나 원본 픽셀을 모든 viewport에 고정하지 않는다.
- 폰트 fallback과 로딩 전후 레이아웃을 확인한다. 외부 폰트·이미지 사용 시 라이선스와 실패 대체 동작을 검토한다.
- 이미지에 용도에 맞는 대체 텍스트를 제공한다. 장식 이미지는 읽기 흐름에서 제외하고 크기 또는 비율을 예약한다.
- 애니메이션은 상태 이해를 돕는 범위에서 사용하며 reduced motion을 존중한다.
- 사용자 테마를 제품 범위 밖에서 임의로 추가하지 않는다. 지원하는 테마에서 focus·disabled·error·hover가 구분되는지 확인한다.

## 6. 검증 기록

키보드만으로 핵심 흐름 완료, focus 복귀, 확대·폭 변경, 직접 URL 진입, 실패 복구를 기록한다. 자동 검사 통과를 수동 접근성 검토의 대체 증거로 사용하지 않는다. 실제 실행 브라우저와 viewport는 [테스트 기준](../ARCHITECTURE/TESTING.md)에 따라 남긴다.
