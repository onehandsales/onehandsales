# Mock 우선 개발과 API 전환

기준일: 2026-11-20 KST. [결정 005](../DECISIONS/005_web_mock_first_standard.md)를 구현할 때 적용한다. 아래 adapter/provider 구조는 목표 규칙이며 현재 구현 완료를 뜻하지 않는다.

## 1. 개발 순서와 산출물

| 순서 | 작성·구현 내용 | 다음 단계로 넘길 증거 |
| --- | --- | --- |
| 흐름 정의 | Gummble 단계, 진입·종료·분기, 공식 문서와의 차이 | 출처 링크, 관찰·문서·가정·미확인 구분 |
| 화면·상태 설계 | route, 컴포넌트, 표시 데이터, 정상·빈 결과·로딩·오류 | 화면별 상태표와 수용 기준 |
| mock 구현 | 공통 데이터 저장소, 비동기 계약, 기능 hook, 화면 연결 | 목록에서 생성한 항목을 상세·편집에서도 확인 |
| 웹 UX 검증 | 뒤로가기·재진입·키보드·반응형·실패 복구 | 실행한 시나리오와 실제 결과 |
| 계약 확정 | 검증된 UX + Bonsai 공식 도움말 + 공식 API 문서 대조 | 엔터티·관계·권한·업무 상태·오류·미확인 목록 |
| 실제 연동 | 우리 API 계약에 맞는 HTTP adapter와 회귀 검증 | mock 결과와 실제 서버 결과를 분리한 기록 |

FE 구현 중 발견한 데이터 요구를 마지막까지 미루지 않는다. 단, 필수값·관계 개수·가격·권한·삭제 정책을 mock 편의 때문에 확정하지 않는다. Bonsai 공개 API에 없는 화면 기능을 미지원으로 단정하거나 추정 endpoint를 만들지 않는다.

## 2. 데이터 경계

```text
Page / Feature UI
        ↓
Feature hook (query / mutation)
        ↓
Feature data-source interface
        ↓
Mock adapter + shared fixture store
또는 HTTP adapter + 기존 API client (계약 확정 이후)
```

- UI와 hook은 선택된 계약에 의존한다. 컴포넌트에서 fixture를 import하거나 `if (mock)`으로 분기하지 않는다.
- 초기에는 mock adapter만 구현해도 된다. 미래의 HTTP endpoint나 범용 repository framework를 미리 만들지 않는다.
- 앱의 provider/factory에서 의존성을 선택한다. 모드 누락·잘못된 값은 명시적으로 실패시키며 실제 서버로 자동 fallback하지 않는다.
- 업무 데이터 호출은 해당 기능 adapter로 모은다. 화면에서 직접 `fetch`, 기존 범용 CRM API 또는 Supabase 데이터 테이블을 호출하지 않는다.
- mock과 HTTP의 성공·실패·취소 형태를 같은 FE 계약으로 표현한다. 전송 DTO 변환은 HTTP adapter 책임이다.
- 타입은 필요한 기능 단위로 정의한다. 모든 Bonsai 기능을 하나의 거대한 서비스 interface로 묶지 않는다.

## 3. mock 데이터 품질

| 항목 | 필수 기준 |
| --- | --- |
| 공유 | 같은 항목의 목록·상세·검색·편집은 같은 저장소와 ID를 사용 |
| 관계 | fixture의 참조 ID가 실제 fixture에 존재하며 변경 후 연결 화면도 갱신 |
| 비동기 | Promise 기반 반환, 조회 취소 전달, 지연·실패 시나리오를 선택 가능 |
| 결정성 | 기준 시각·ID 생성·seed를 통제하고 테스트 시작 시 초기화 |
| 상태 | 생성·수정·삭제 등 구현한 행동이 저장소에 반영되며 토스트만 띄우지 않음 |
| 격리 | 테스트·사용자·workspace 간 데이터 혼합 방지, 읽은 객체의 직접 변경 방지 |
| 저장 수명 | 메모리 또는 브라우저 저장 여부와 새로고침 시 복구·초기화 동작을 명시 |
| 개인정보 | 가상 이름·주소·문서를 사용하고 실제 계정·고객 데이터를 fixture에 복사하지 않음 |

메모리 저장이 기본 출발점이다. 새로고침 후 유지가 필요한 검증에서만 브라우저 저장을 선택하고 seed 버전·초기화 방법·손상 데이터 복구를 함께 구현한다. 브라우저 저장 성공을 서버 저장 성공으로 표시하지 않는다.

빈 데이터와 검색 결과 없음, 조회 실패와 권한 제한은 서로 다른 상태로 준비한다. 취소 시 이미 반영된 변경이 되돌아가는지 여부는 별도 정책이며, 요청 중단만으로 rollback을 가정하지 않는다.

## 4. 인증과 네트워크

2026-11-20 소스 확인 시 User Web의 `app-providers.tsx`는 실제 AuthProvider를 포함한다. 따라서 업무 route만 mock으로 바꾸어도 인증 네트워크까지 사라지는 것은 아니다.

- **완전 독립 검증:** mock 진입점에서 fake session/workspace와 mock 업무 provider를 함께 조립한다. 기존 실제 인증 경로와 관리자 권한 검증은 보존한다.
- **실제 로그인 유지:** 인증 호출과 허용할 부트스트랩 호출을 이름·목적으로 열거한다. 이 경로는 “BE와 완전히 분리됨”으로 보고하지 않는다.
- 어느 방식을 택했는지 기능 문서와 테스트에 기록한다. 임의의 기본 사용자 ID를 실 API에 전송하지 않는다.
- 브라우저 네트워크 또는 E2E에서 허용한 인증·정적 리소스 외의 업무 API 요청이 없는지 확인한다. 요청이 실패했다는 사실만으로 미연결을 증명하지 않는다.
- 개발용 시나리오 선택·reset은 개발 도구 영역에서 제공한다. 실제 서비스 사용자에게 mock 내부 구조를 제품 UX로 노출하지 않는다.
- 운영 빌드에 mock 진입점이 포함될 경우 별도 데모 목적과 진입 제한을 명시한다. 일반 서비스 로그인에서 mock으로 자동 진입하지 않는다.

## 5. 기능별 작성 양식

각 기능의 설계·리뷰 기록에는 다음 항목을 채운다. 별도 파일이 불필요한 작은 변경은 PR 설명에 기록해도 된다.

| 항목 | 기록할 내용 |
| --- | --- |
| 근거 | Gummble flow/screen, 공식 문서 URL·조회일, 실제 계정 확인 여부 |
| 사용자 목표 | 시작 상태 → 사용자 행동 → 확인 가능한 종료 상태 |
| route·상태 | URL에 남길 값, 임시 UI 상태, 폼 초안, 취소·재진입 동작 |
| 데이터 계약 | 입력·결과·오류·nullable·관계 ID·정렬·페이지 처리의 임시 정의 |
| mock 시나리오 | seed, 저장 수명, 정상·빈 결과·실패·지연·권한 상태 |
| 네트워크 | 업무 mock, 인증 방식, 허용 요청 |
| 검증 | 기대 결과·실제 결과·미검증 항목 |
| 연동 전 질문 | 서버에서 확인할 업무 규칙·권한·동시 수정·영속성 |

## 6. 실제 API로 전환할 조건

1. 핵심 업무 흐름의 화면과 mock 상태 전환이 수용 기준을 통과한다.
2. 기능 간 공유 데이터와 관계, 권한, 금액·날짜 의미를 문서와 대조한다.
3. 우리 API의 요청·응답·오류·정렬·페이지 처리와 DB 변경 계획을 승인된 범위에서 확정한다.
4. HTTP adapter를 추가하고 같은 UI 시나리오를 실제 테스트 데이터로 검증한다.
5. 서버 저장·재조회·권한·실패 복구를 별도 확인한 뒤 연동 완료로 표시한다.

이 규칙은 DB 테이블 삭제나 기존 BE 제거를 승인하지 않는다. 상세 상태 규칙은 [상태·데이터](STATE_AND_DATA.md), 검증 명령은 [테스트](TESTING.md)를 따른다.
