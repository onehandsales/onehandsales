# 웹 프론트엔드 엔지니어링 리뷰

기준일: 2026-11-20 KST. 신규·수정 범위에 적용한다. 해당하지 않는 항목은 N/A와 이유를 기록하고, 미실행 검증은 통과로 표시하지 않는다.

## 1. 범위와 출처

- [ ] 사용자 요청과 기존 변경을 확인하고 불필요한 재구성·도메인 정책 추가를 피했는가?
- [ ] Bonsai 화면 관찰·현재 공식 문서·실제 계정 결과·구현 가정을 구분했는가?
- [ ] 사용자 목표의 시작·행동·종료·취소·실패를 수용 기준으로 적었는가?
- [ ] 현재 구현, 목표 규칙, mock 완료, 실제 연동 완료를 구분했는가?

## 2. 구조와 컴포넌트

- [ ] page·feature·shared UI·adapter의 책임과 import 방향이 명확한가?
- [ ] 컴포넌트의 props·callback·controlled 상태 소유자가 분명한가?
- [ ] 분리·공통화에 실제 책임 또는 사용처 근거가 있고 범용화가 과도하지 않은가?
- [ ] 두 앱 사이 feature 직접 import와 순환 의존이 없는가?
- [ ] 새 의존성을 추가했다면 기존 도구 대비 필요·크기·접근성·유지보수를 검토했는가?

## 3. 데이터와 mock

- [ ] 신규 Bonsai 업무 UI가 mock 계약을 사용하고 fixture·실 API를 직접 호출하지 않는가?
- [ ] mock/live 선택이 조립 지점에 있으며 실제 서버 자동 fallback이 없는가?
- [ ] 실제 인증 유지 또는 mock 진입 방식과 허용 네트워크 요청을 기록했는가?
- [ ] 동일 ID의 생성·수정·삭제가 목록·상세·관련 화면에 일관되게 반영되는가?
- [ ] seed·기준 시각·초기화·저장 수명이 결정적이고 가상 데이터임이 구분되는가?
- [ ] 기존 live 화면에서 API에 없는 상태·관계·성공 결과를 mock으로 몰래 채우지 않는가?
- [ ] FE 임시 타입을 확정 DB·공식 API 계약으로 오해할 표현이 없는가?

## 4. 상태와 비동기

- [ ] URL·폼·local state·Query·mock 원본 데이터의 소유권이 중복되지 않는가?
- [ ] query key에 결과를 바꾸는 범위·조건이 포함되고 사용자·workspace·데이터 모드가 격리되는가?
- [ ] 요청 취소, 빠른 대상 변경, 로그아웃 후 늦은 응답을 처리하는가?
- [ ] 저장 대상과 입력값이 제출 시점에 고정되고 중복 제출·재시도·실패 복구가 안전한가?
- [ ] 저장 후 관련 조회·합계·선택 상태가 갱신되고 무관한 캐시를 과도하게 지우지 않는가?
- [ ] null·0·빈 결과·부분 집계·금액·날짜 의미가 보존되는가?

## 5. 웹 UX와 접근성

- [ ] 직접 URL·새로고침·뒤로/앞으로가기·새 탭 링크·잘못된 ID가 의도대로 동작하는가?
- [ ] 키보드만으로 핵심 흐름을 완료하고 포커스 위치를 확인할 수 있는가?
- [ ] 모달의 초점 이동·복귀·Esc·배경 비활성과 메뉴의 조작 방식이 적절한가?
- [ ] label·오류 연결·아이콘 이름·표 header·버튼 type이 올바른가?
- [ ] 로딩·빈 데이터·검색 결과 없음·오류·권한 제한·재시도가 구분되는가?
- [ ] 캡처 viewport, 좁은 폭, 확대, 긴 데이터, 스크롤·sticky·overlay를 확인했는가?
- [ ] IME 입력·터치·reduced motion 등 변경 기능에 해당하는 브라우저 조건을 확인했는가?

## 6. 주석·품질·보안

- [ ] 모든 신규·동작 변경 컴포넌트·hook·함수에 `// 기능 :` 한글 한 문장 주석이 있는가?
- [ ] 복잡한 흐름의 번호 주석이 상태 전환과 이유를 설명하며 코드 한 줄 번역에 그치지 않는가?

- [ ] 권한을 UI에서만 판정하거나 비밀 값을 번들·URL·로그에 노출하지 않는가?
- [ ] 실제 병목 또는 회귀 위험에 맞게 성능을 확인했는가?
