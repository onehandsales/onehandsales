# 025 — Bonsai 단일 UX 기준

Status: Accepted
Updated: 2026-11-17

[PM 036](../../PM_AGENT/DECISIONS/036_bonsai_benchmark_transition.md)에 따라 Bonsai의 화면·사용자 흐름·상태·상호작용을 재현한다. 조사 도구는 Gummble이다.

## 근거 사용

- Gummble에서 Bonsai 앱·screen·flow를 찾고 식별자·원본 링크·캡처 조건을 기록한다.
- Bonsai 공식 도움말로 업무 의미, 공식 API로 공개 계약, 실제 계정으로 상태와 권한을 대조한다.
- 화면을 보지 않은 배치·크기·저장 방식·삭제 동작을 확정하지 않는다.
- 다른 버전의 Proposal과 Document Builder 화면을 하나의 흐름으로 섞지 않는다.
- 공식 자료와 화면이 다르면 [조사 정본](../PLANNING/BONSAI_BENCHMARK_RESEARCH.md)에 차이와 미확인을 남긴다.

## 제품 범위

고객·거래·견적·합의 문서·프로젝트·작업·시간·청구·입금을 연결하며 포털·팀·인력·보고서·설정까지 조사한다. 대표·영업사원·프로젝트 담당자·실무자·고객을 포함하고 개인 전용 메뉴로 제한하지 않는다.

테이블 가로 스크롤, 상세 패널/모달/페이지, 모바일 전환, 저장 방식은 해당 화면의 근거와 접근성을 함께 검토한다. 과거의 일괄 금지나 특정 패널 고정 규칙은 적용하지 않는다.

## Figma와 구현 착수

Bonsai에 이미 반영된 제품·UX 결정을 우리 구현의 출발점으로 삼는다. 확보한 Gummble·실계정 원본을 기준으로 실제 프런트엔드 화면을 만들며 검토할 수 있다. **Figma 제작이나 MCP를 통한 Figma 화면 복제는 필수 선행 단계가 아니다.**

- PM은 재현할 기능 범위·연결 업무·완료 기준을 정리한다.
- UXUI는 원본의 화면·문구·상호작용·상태·역할별 차이를 확인한다.
- Software는 확인한 동작에 맞춰 DB·API·프런트엔드를 설계·구현한다.
- Gummble 자료 확보 이후 저장 시점·권한·계산·삭제 영향 등 화면에 없는 규칙을 공식 도움말·API와 실계정으로 보완한다.
- mock은 기존 React 프런트엔드에 임시 데이터를 넣어 만든 화면도 포함한다. 전체 화면을 별도 디자인 도구로 완성하거나 별도의 일회용 프로토타입을 만들어야 하는 것은 아니다.
- 기능별로 원본 확인 → 동작 정리와 화면 제작·계약 설계 → 실제 저장·조회 연결 → 원본 비교를 반복한다. 화면 제작과 계약 초안은 병행하되 실제 API 연동 전에 해당 계약을 확정한다.
- 구현 착수 기준은 해당 기능의 원본과 동작을 설명할 수 있는 상태다. 미확인 부분은 명시하며, 전체 제품 조사나 Figma 완성을 기다리는 조건으로 확대하지 않는다.

Figma는 이후 차별화·새 흐름 설계·여러 디자인안 비교가 필요할 때 선택적으로 사용한다. 실제 저장되지 않는 화면과 구현·검증이 완료된 기능은 구분한다.

## 확인 상태와 완료

2026-11-17 공식 주요 자료를 조회했다. Gummble 도구 호출·Bonsai 화면 수집·실계정 동작 검증은 수행하지 않았다. 연결 성공과 기능 검증을 분리해 기록한다.

각 화면의 근거·행동·상태·API·권한·DB 요구를 연결하고 [기능 대응표](../../PM_AGENT/PLANNING/BONSAI_FEATURE_PARITY_MATRIX.md)에서 전체 차이를 관리한다. Gummble 자료가 없는 기능은 공식 자료·실계정으로 보완하며 범위에서 제거하지 않는다.
