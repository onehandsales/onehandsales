# 확정 결정

Status: Current PM Baseline
Date: 2026-09-12

## 1. 현재 제품 방향

제품명은 `OneHand CRM`으로 고정한다.

브랜드 표기:

- 제품명: `OneHand CRM`
- 붙여 쓰는 브랜드 표기: `OneHandCRM`
- 도메인/slug/code 표기: `onehandcrm`

OneHand CRM의 핵심 문장은 다음이다.

> CRM을 배우거나 설계할 필요 없이, 내 일에 맞는 CRM이 바로 준비된다.

OneHand CRM은 고정된 영업 CRM도 아니고, 사용자가 처음부터 직접 설계해야 하는 빈 CRM builder도 아니다. 사용자가 무슨 일을 하는지 알려주면 그 일에 맞는 CRM 구조가 먼저 준비되고, 필요해지는 순간 업무 언어로 자연스럽게 확장되는 No Setup CRM을 목표로 한다.

제품 철학은 다음 문장으로 고정한다.

> Ready-made, but never locked.

## 2. 제품 포지션 결정

확정:

- 직군별 Kit 기반 CRM을 제품 중심에 둔다.
- Kit은 템플릿 파일이 아니라 관리 대상, 관계, 필드, 상태, 기본 보기, 다음 행동을 포함하는 CRM 시작 구조다.
- 다음 CRM Core는 Workspace/Kit/Object/Attribute/Relationship/Record/View 기반으로 별도 설계한다.
- 사용자는 내부 데이터 모델 용어를 배우지 않아도 되어야 한다.

하지 않음:

- 기존 고정형 고객사 관리 도메인을 되살리지 않는다.
- Company/Product/Deal을 OneHand CRM 전체의 전역 기본 도메인으로 두지 않는다.
- CRM builder처럼 사용자가 처음부터 Object/Field/Relation을 직접 설계하게 하지 않는다.
- 결제/구독을 제품 가설 검증보다 먼저 구현하지 않는다.

## 3. 현재 활성 도메인

현재 코드 기준 활성 도메인:

- User/Auth
- Error Report
- Support Request
- Public Contact Request
- Health
- Admin 권한 확인

현재 구현은 고정형 고객사 관리 기능을 제거한 전환 상태이며, 인증/계정/지원 접수/공개 문의 foundation을 유지한다.

## 4. Backend 결정

- 모든 사용자 업무 API는 현재 사용자 ownership을 검증한다.
- 사용자 API는 `/api/*`, 관리자 확인 API는 `GET /admin/api/me`로 분리한다.
- 관리자 API는 `GET /admin/api/me`만 유지한다.
- 공개 문의는 비로그인 접수 API로 유지하며 문의자가 입력하는 회사명과 회사 규모를 보존한다.

공개 문의의 회사명과 회사 규모는 CRM Company record가 아니라 문의 원문 필드다.

## 5. Frontend 결정

- 로그인 이후 업무 화면은 `/app` 아래에 둔다.
- 현재 User Web 활성 앱 화면은 `/app`과 `/app/more`다.
- `/app/contacts/*`, `/app/products/*`, `/app/deals/*`, `/app/export`는 현재 `/app`으로 redirect한다.
- 고정형 고객사 관리 화면은 현재 활성 화면이 아니다.
- 계정 설정은 보호 route 위의 query 기반 모달로 제공한다.
- Admin Web은 access token 권한 확인 화면만 유지한다.

## 6. DB 결정

- 현재 활성 Prisma 모델은 `User`, `UserOAuthAccount`, `AuthDevice`, `AuthSession`, `ErrorReport`, `SupportRequest`, `PublicContactRequest`다.
- Workspace/Kit/Object/Attribute/Relationship/Record/View는 아직 구현된 DB 모델이 아니다.
- 다음 CRM Core는 기존 고정 테이블을 되살리지 않고 새 기준으로 설계한다.

## 7. Workspace와 Team 결정

- Workspace는 후속 CRM Core의 기본 제품 개념으로 본다.
- MVP에서는 개인 사용자가 기본 Workspace를 자동으로 받는 흐름을 우선한다.
- Team/조직 권한은 Workspace와 연결될 수 있지만 현재 MVP의 핵심 범위가 아니다.
- Team을 활성 기능처럼 문서화하려면 별도 PM 결정과 Software 설계가 필요하다.

## 8. 용어 결정

- Company/Product/Deal은 전역 기본 도메인이 아니다.
- 다만 특정 직군 Kit 안에서는 `회사`, `상품`, `계약`, `딜` 같은 업무 언어를 사용할 수 있다.
- 문서에서 현재 구현 기능과 후속 제품 개념을 섞지 않는다.
- `OneHand Sales`, `onehand.sales`는 과거 명칭 또는 역사적 문맥에서만 사용한다.

## 9. 문서 결정

- 루트 `README.md`를 최상위 제품 방향 기준으로 둔다.
- PM_AGENT는 루트 방향을 PRD, MVP 범위, Kit 전략, 결정 기록으로 구체화한다.
- 문서는 현재 코드에 남은 기능만 활성 구현 기능으로 설명한다.
- 삭제된 고정형 도메인 문서는 활성 API, 화면, DB 모델처럼 설명하지 않는다.
