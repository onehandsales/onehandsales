# Bonsai 학습 계획과 초기 타깃 고객

작성 기준일: 2026-11-17

## 먼저 읽을 결론

**지금 할 일은 Bonsai에서 고객 한 명의 문의가 견적, 계약, 실제 작업, 청구로 이어지는 과정을 이해하는 것이다.** 기능 이름을 전부 외우기보다, 같은 고객의 일을 처음부터 끝까지 따라가며 배운다.

**초기 타깃으로는 고객별 견적을 작성하고 여러 프로젝트를 수행하는 소규모 웹·앱 개발사와 디자인 스튜디오를 추천한다.** 대표나 프로젝트 담당자가 영업, 견적, 작업 배정, 청구를 함께 챙기는 팀을 먼저 만나본다. 규모의 숫자보다 이런 업무 방식이 중요하다.

이 추천은 검증할 가설이다. 해당 업종의 구매 수요가 확인됐다는 뜻은 아니다. 청소업을 포함한 다른 서비스업에도 같은 흐름이 있는지 비교한다.

오늘은 아래의 **가상 개발 프로젝트 하나**를 읽고, Bonsai에서 `거래 → 견적 → 프로젝트 → 청구서`가 어떻게 연결되는지 확인하면 된다. 세부 기능과 출처는 [기능 지도와 확인 사항](CRM_Bonsai_기능지도와_확인사항.md)에 모았다.

## 1. 지금까지 선택한 방향

| 구분 | 현재 내용 |
| --- | --- |
| 만들고 싶은 경험 | 여러 거래를 한눈에 보고, 특정 거래를 열어 상세 내용을 확인한다. 앱 안에서 견적을 작성하고, 수주 후 실제 작업과 청구까지 관리한다. |
| 만드는 방식 | 하나의 제품을 충분히 이해하고 따라 만든 뒤, 완성 후 자신의 방식으로 변경한다. |
| 우선 학습할 제품 | Bonsai. 견적을 프로젝트와 작업으로 연결하는 공식 기능이 현재 요구에 맞아 우선 조사한다. |
| 검증할 고객 가설 | 고객마다 작업 범위와 금액이 달라지는 소규모 개발·디자인 서비스 팀. |
| 아직 정하지 않은 것 | 최종 업종, 구매자, 복제할 제품 버전과 전체 범위, 가격, 국내 결제·세무 연동 방식. |

이 문서는 연구 방향을 정리한다. 저장소의 기존 folk 기준 제품·UX 결정이나 구현을 Bonsai 기준으로 변경한 것은 아니다.

## 2. 개발 프로젝트 하나로 이해하기

다음 회사, 금액, 사건은 설명을 위한 가상 예시다. 원화 표기는 이해를 위한 것이며 Bonsai의 한국 결제 지원을 검증했다는 뜻은 아니다. 세금 계산은 이 예시에서 생략한다.

당신은 외주 개발팀의 대표다. 고객사 A가 예약 사이트 제작을 문의했다. 동시에 B사와 C사의 다른 일도 진행 중이다.

| 단계 | 실제로 생기는 일 | 도구에서 관리할 내용 | 도움이 되는 이유 |
| --- | --- | --- | --- |
| 고객 | A사 담당자 김대리가 연락한다. 나중에는 회계 담당자도 참여한다. | 회사와 연락 담당자 | 프로젝트가 바뀌어도 누구와 이야기했는지 찾을 수 있다. |
| 거래 | A사의 예약 사이트는 견적 협의 중, B사의 리뉴얼은 계약 대기 중이다. | 거래별 단계, 예상 금액, 담당자, 다음 할 일 | 대표가 오늘 어느 거래에 연락해야 하는지 판단한다. |
| 견적 | 로그인 200만 원, 예약 기능 500만 원, 관리자 화면 300만 원을 제안한다. | 작업 항목, 수량·단가, 합계, 설명 | “총 1,000만 원”에 무엇이 포함됐는지 고객과 확인한다. |
| 합의 | 고객이 범위와 금액을 확인하고 문서에 서명한다. | 제안·계약 문서와 서명 상태 | 작업 도중 처음 합의한 내용을 다시 확인할 수 있다. |
| 프로젝트 | 수주한 예약 사이트를 실제로 만든다. | 프로젝트, 작업, 담당자, 마감일 | 영업에서 약속한 내용을 수행하는 사람이 이어받는다. |
| 추가 요청 | 고객이 알림 기능을 100만 원에 추가하자고 한다. | 추가 견적·합의, 작업, 청구 반영 여부 | 추가 일을 하고도 돈을 빠뜨려 받는 상황을 점검한다. |
| 청구 | 계약금 500만 원을 받고, 완료 후 남은 600만 원을 청구한다. | 청구서, 지급 기한, 입금액, 미수 잔액 | 작업 완료와 돈을 받은 상태를 구분한다. |

표의 효과는 업무 흐름에 대한 설명이다. 모든 단계가 Bonsai에서 자동으로 연결되거나, 추가 요청이 관련 문서에 자동 반영된다는 뜻은 아니다. 실제 학습에서는 **어디까지 자동으로 이어지고 어디서 사람이 확인·수정하는지**를 기록한다.

### 개발자가 특히 구분해야 할 네 가지

- **고객:** 일을 맡기는 회사나 사람. A사는 예약 사이트 제작과 유지보수를 각각 의뢰할 수 있다.
- **거래:** 성사시키려는 개별 영업 건. 계약 전의 예약 사이트 제작 건도 거래다.
- **프로젝트:** 실제 수행할 일의 묶음. 예약 사이트를 만들면서 작업과 일정을 관리한다.
- **청구서:** 지급을 요청하는 문서. 프로젝트 하나에서도 계약금·잔금 등 여러 차례 청구할 수 있다.

따라서 “고객 A사 = 거래 하나 = 프로젝트 하나 = 청구서 하나”로 생각하면 업무를 놓치기 쉽다. 이것은 개념을 이해하기 위한 설명이며, Bonsai 내부 DB 구조나 관계 개수를 그대로 확인한 결과는 아니다.

## 3. 어떤 순서로 배우면 되는가

같은 A사 예시를 계속 사용한다. 학습 순서는 구현 범위를 줄이기로 한 결정이 아니다. 전체를 따라 만들더라도 먼저 중심 흐름을 이해하고 기능을 넓혀간다.

| 순서 | 살펴볼 것 | 학습을 마치면 답할 수 있어야 할 질문 |
| --- | --- | --- |
| 1 | 회사·담당자·거래 목록과 상세 | 같은 회사의 여러 거래를 어떻게 구분하고, 다음 연락을 어디에 기록하는가? |
| 2 | 견적 작성과 문서 작성·서명 | 견적의 작업 항목과 금액이 고객에게 보내는 문서에 어떻게 들어가는가? |
| 3 | 견적에서 프로젝트 만들기 | 견적의 어느 값이 프로젝트·작업으로 넘어가고, 무엇을 다시 입력해야 하는가? |
| 4 | 작업·시간·비용·예산 | 누가 무엇을 언제까지 하는지, 예상보다 일이 늘어났는지 어떻게 파악하는가? |
| 5 | 청구와 입금 기록 | 계약금·잔금·부분 입금·미수 상태를 어떻게 구분하는가? |
| 6 | 고객 포털과 권한 | 고객에게 무엇을 보여주며, 내부 비용이나 다른 고객의 정보는 어떻게 가리는가? |
| 7 | 반복 업무·자동화·보고서·팀 운영 | 비슷한 다음 프로젝트에서 무엇을 재사용하고, 어떤 조건에서 어떤 동작이 실행되는가? |

처음에는 정상적인 수주 한 건을 끝까지 따라간다. 그다음 **견적 수정, 추가 작업, 거래 실패, 일정 지연, 부분 입금**을 각각 넣어본다. 이런 상황에서 정보가 어디에 남는지 이해해야 화면을 따라 만들 때 동작도 설계할 수 있다.

Nicelydone에서는 화면과 사용자 흐름을, 공식 문서에서는 기능의 조건을, 실제 계정에서는 동작 결과를 확인한다. 아직 조회하지 않은 화면과 직접 실행하지 않은 동작은 미확인으로 남긴다.

## 4. 왜 개발·디자인 팀을 첫 타깃 후보로 추천하는가

Bonsai는 공식적으로 에이전시의 고객·프로젝트·팀 관리를 설명하고, 디자인·마케팅·컨설팅·소프트웨어 개발 등의 분야를 제시한다. 따라서 개발·디자인 업무로 학습하는 것은 제품이 설명하는 사용 방식과 연결된다. [공식 에이전시 소개](https://www.hellobonsai.com/software/agencies)

여기에 사용자가 개발자라는 점을 함께 고려했다. “로그인 기능을 추가하면 견적과 작업량이 달라진다”는 상황은 직접 이해하고 결과를 판단하기 쉽다. **학습하기 좋은 출발점이라는 판단과, 사업적으로 돈을 내는 고객이라는 검증은 별개다.**

우선 만나볼 고객은 다음과 같은 팀이다.

- 외부 고객에게 개발·디자인 등의 서비스를 판매한다.
- 고객마다 견적의 작업 항목, 금액, 일정이 달라진다.
- 여러 고객의 일을 동시에 진행한다.
- 대표나 담당자가 문의·견적·작업·청구 사이에서 정보를 다시 옮긴다.
- 추가 요청, 변경된 합의, 청구할 금액 중 하나라도 놓치는 문제가 있다.

첫 구매자 후보는 업무 전체와 지출을 결정하는 대표 또는 운영 책임자다. 매일 사용하는 사람은 대표, 프로젝트 담당자, 실무자일 수 있다. 고객사는 견적 확인·서명·자료 전달·청구 확인을 위해 접속하는 별도의 사용자다. 이 역할 구분도 인터뷰에서 확인한다.

| 타깃 후보 | 가상 업무 | 현재 판단 |
| --- | --- | --- |
| 웹·앱 개발사, 디자인 스튜디오 | 사이트 제작 견적 → 개발·디자인 작업 → 검수 → 계약금·잔금 청구 | 첫 학습·고객 검증 대상으로 추천한다. |
| 마케팅·콘텐츠·영상 제작사, 컨설팅 업체 | 제작·자문 범위 협의 → 수행 → 수정·납품 → 청구 | 같은 흐름이 반복되는지 비교할 인접 후보들이다. |
| 누나와 같은 청소 서비스 업체 | 현장별 견적 → 청소 수행 → 확인 → 청구 | 반드시 비교할 실제 사례다. 현장 배치·이동·면적별 가격 계산의 중요도를 추가로 확인한다. |

이 표는 특정 업종을 지원 대상에서 제외하는 결정이 아니다. **처음 누구의 업무를 깊이 이해할지 정하는 순서**다.

### 누나의 요구는 어디까지 같은 문제인가

고객별 요구, 작업 범위, 가격, 진행 상태, 청구를 연결한다는 점은 같은 문제다. 다만 청소업에서 중요한 기능이 일반 프로젝트 관리만으로 충족되는지는 별도로 봐야 한다.

예를 들어 “화장실 집중 청소”를 견적 항목과 작업 설명으로 적는 것과, “지역·평수·오염도에 따라 가격을 자동 계산한다”는 것은 다른 기능이다. 세율을 입력하는 것과 “세금 포함 총액 200만 원을 입력하면 공급가액을 역산한다”도 다르다. 후자의 동작은 현재 Bonsai에서 확인되지 않았다. [상세 확인 사항](CRM_Bonsai_기능지도와_확인사항.md)

## 5. 학습하면서 타깃을 검증하는 방법

제품을 끝까지 따라 만들겠다는 방향을 유지하면서도, 고객의 실제 업무는 학습과 함께 확인한다. “이런 CRM을 쓰실래요?”보다 최근 끝낸 일 한 건을 기준으로 이야기를 듣는다.

1. 문의를 어디서 받았고, 고객 정보와 다음 연락은 어디에 적었는지 확인한다.
2. 개인정보를 가린 실제 견적서를 보며 작업 범위와 가격이 어떻게 정해졌는지 듣는다.
3. 수주 후 누가 작업을 맡았고, 견적 내용을 어디에 다시 입력했는지 확인한다.
4. 추가 요청이 있었는지, 누가 합의했고 작업과 금액에 어떻게 반영했는지 확인한다.
5. 청구와 입금 확인을 누가 하며, 놓치거나 늦어진 일이 있었는지 듣는다.
6. 이 문제를 해결하기 위해 지금 쓰는 도구·시간·비용과, 새 도구를 시험해 볼 의향을 확인한다.

여러 팀에서 같은 불편이 반복되고 실제 업무로 시험해 보려 한다면 타깃 가설을 유지할 근거가 생긴다. 반대로 견적·청구 연결보다 현장 배차, 재고, 다른 시스템 연동이 핵심이라면 타깃이나 제품 선택을 다시 검토한다. 단순히 “좋아 보인다”는 반응만으로 구매 수요가 있다고 판단하지 않는다.

## 6. 다음에 남길 학습 결과

첫 결과물은 기능 목록의 암기가 아니라 **A사 한 건의 흐름을 설명하는 기록**이다. 단계마다 아래 항목을 채운다.

| 기록 항목 | 기록할 내용 |
| --- | --- |
| 사용자와 목적 | 대표가 견적을 보낸다 / 실무자가 작업을 끝낸다 / 고객이 청구서를 확인한다. |
| 화면과 행동 | 어떤 화면에서 무엇을 입력하고 어떤 버튼을 누르는가? |
| 데이터 연결 | 무엇이 새로 생기고, 기존 거래·견적·프로젝트·청구서 중 무엇과 연결되는가? |
| 상태 변화 | 전송·서명·수주·완료·청구·입금을 각각 어떤 상태로 나타내는가? |
