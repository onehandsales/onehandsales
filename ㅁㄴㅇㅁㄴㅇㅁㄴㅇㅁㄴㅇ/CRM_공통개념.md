# CRM 공통 개념과 청소 사업 예시

CRM은 고객과 관련된 정보를 모아, 누가 어떤 관계를 맺고 있고 다음에 어떤 일을 해야 하는지 관리하는 소프트웨어다. 연락처를 저장하는 데서 시작해 영업, 고객 지원, 서비스 제공 등 여러 업무로 이어질 수 있다.

이 목록의 20개는 모두 같은 범위의 제품이 아니다. 연락처를 찾는 도구, 고객과 통화하는 도구, 상담을 처리하는 도구, 회원 구독을 운영하는 도구도 섞여 있다. 따라서 아래는 **일반적인 CRM을 이해하기 위한 공통 개념**이며, 20개 모두가 동일한 기능을 제공한다는 체크리스트가 아니다.

## 고객과 관련해서 기억해야 할 것

가상의 청소 회사 ‘맑은청소’가 ‘한빛학원’과 거래한다고 생각해 보자. 한빛학원은 매월 청소를 맡기지만, 이번 달에는 창문을 제외하고 다음 달에는 창문을 추가하려고 한다.

| 공통 개념 | 쉬운 뜻 | 맑은청소의 예시 |
| --- | --- | --- |
| 사람과 회사 | 연락하는 사람과 거래하는 조직 | 한빛학원이라는 회사와 그곳의 김실장 |
| 고객 정보 | 다음에도 참고할 정보 | 연락처, 주소, 담당자, 평소 요청사항 |
| 거래 또는 영업 기회 | 특정한 계약·주문으로 이어질 수 있는 한 건 | 이번 달 정기 청소 협의 건 |
| 활동과 이력 | 어떤 일이 있었는지 남긴 기록 | 전화 상담, 견적 전달, 작업 범위 변경 요청 |
| 할 일 | 앞으로 수행할 행동 | 내일까지 수정 견적을 보내기 |
| 담당자 | 그 일을 맡은 내부 직원 | 견적은 대표, 현장 확인은 팀장 |
| 진행 단계 | 현재 일이 어디까지 왔는지 | 문의 접수 → 현장 확인 → 견적 전달 → 합의 |
| 검색과 분류 | 필요한 대상만 찾는 방법 | 이번 주 견적을 보내야 하는 거래 찾기 |

이 개념들은 제품에 따라 다른 이름과 구조로 나타난다. Attio는 객체·레코드·속성·목록을 설명하고, Capsule은 연락처와 연결된 프로젝트를 설명하며, folk는 기본 연락처 필드와 그룹별 필드를 구분한다. [Attio 데이터 모델](https://attio.com/help/reference/attio-101/attios-data-model/define-your-data-model-objects-lists-and-views), [Capsule 프로젝트](https://capsulecrm.com/support/projects-and-events/adding-projects/), [folk 연락처 필드](https://help.folk.app/en/articles/4991006-contact-fields)

## 고객 정보와 이번 거래의 정보는 구분해서 생각한다

한빛학원의 연락처는 여러 거래에서 함께 참고할 수 있다. 반면 ‘창문 제외’, ‘이번 작업의 합의 금액’, ‘세금 포함으로 바꿔 달라는 요청’은 거래마다 달라질 수 있다.

| 정보의 성격 | 예시 | 구분하는 이유 |
| --- | --- | --- |
| 고객에게 계속 참고할 정보 | 김실장 연락처, 평소 연락 가능한 시간 | 다음 거래에서도 사용한다. |
| 현장에 관한 정보 | 본점 주소, 별관 출입 방법 | 같은 고객도 여러 현장을 가질 수 있다. |
| 이번 거래의 조건 | 청소할 공간, 제외할 공간, 항목별 가격, 합의한 총액의 기준 | 다른 거래의 조건과 섞이면 안 된다. |
| 변경 기록 | 창문 추가 요청과 수정한 견적 | 무엇이 바뀌었고 어느 내용으로 합의했는지 확인한다. |

이는 사용자 사례를 이해하기 위한 정보 구분이다. 특정 제품이 이 구조를 기본 제공하거나 모든 변경을 자동 보존한다고 주장하는 것은 아니다. 각 제품에서 어떻게 표현하는지는 차별점 문서와 후속 실제 사용 검증으로 확인해야 한다.

## 흔히 있는 기능과 모든 제품에 있지는 않은 기능

| 기능군 | 어떤 일을 돕는가 | 이번 비교에서 주의할 점 |
| --- | --- | --- |
| 연락처와 대상 목록 | 연락할 사람·회사와 정보를 정리한다. | 연락처를 찾아 주는 서비스와 장기 관계를 관리하는 서비스는 목적이 다르다. |
| 메모와 대화 이력 | 이전 대화와 약속을 찾는다. | 직접 적는 방식, 이메일 동기화, AI 요약은 서로 다른 기능이다. |
| 할 일과 진행 상태 | 다음 행동과 담당자를 놓치지 않게 한다. | 영업의 진행 단계와 고객 문의의 처리 상태는 다른 업무를 표현한다. |
| 사용자 정의 항목 | 회사에 필요한 정보를 추가한다. | 새 입력 칸을 만드는 것과 가격 계산·견적 승인 기능을 갖추는 것은 별개다. |
| 자동화와 외부 연동 | 반복 작업이나 데이터 복사를 줄인다. | 이메일을 연결했다고 전화·메신저까지 모두 연결되는 것은 아니다. |
| 견적·계약·청구 | 작업 범위와 금액을 고객에게 제시하고 합의한다. | CRM의 필수 공통 기능으로 가정하지 않는다. |
| 결제와 구독 | 결제 상태와 정기 구독을 관리한다. | 정기 방문 청소의 일정 관리와 회원 구독 관리도 서로 다르다. |
| 고객 포털 | 고객도 들어와 자료·문서·진행 상황을 확인한다. | 내부 직원용 화면과 고객용 화면이 따로 필요하다. |
| AI | 요약, 정보 보강, 초안 작성, 행동 실행 등을 돕는다. | 제품마다 AI가 맡는 일이 다르다. AI라는 표시만으로 비교하지 않는다. |

견적과 서명은 Bonsai의 문서 작성 기능, 구독은 Outseta의 계정 구독 기능, 상담 상태는 Intercom의 티켓 기능에서 각각 확인할 수 있다. 이 차이가 같은 ‘CRM 관련 서비스’ 안에서도 제품의 목적이 달라지는 이유다. [Bonsai 문서 작성](https://help.hellobonsai.com/en/articles/15879228-document-builder-overview), [Outseta 계정 구독](https://go.outseta.com/support/kb/articles/y9gAj0mM/subscribe-an-account), [Intercom 티켓](https://www.intercom.com/help/en/articles/6436600-tickets-explained)

## 비교에 자주 나오는 용어

| 용어 | 쉬운 설명 |
| --- | --- |
| 잠재고객 또는 리드 | 아직 거래하지 않았지만 거래할 가능성이 있는 대상 |
| 영업 기회 또는 딜 | 특정 상품·서비스의 판매를 논의하는 한 건 |
| 파이프라인 | 문의, 상담, 제안, 합의처럼 일을 단계별로 보는 방식 |
| 레코드 | 한 사람, 한 회사, 한 거래 등 개별 기록 하나 |
| 속성 또는 필드 | 이름, 전화번호, 예상 금액처럼 기록에 붙이는 정보 항목 |
| 객체 | 사람, 회사, 거래처럼 같은 종류의 기록을 담는 틀 |
| 보기 | 같은 기록을 표나 단계별 카드 등으로 보여 주는 방식 |
| 워크플로 | 특정 조건이 생겼을 때 이어서 수행할 작업의 규칙 |
| 시퀀스 | 첫 연락, 후속 이메일, 전화 할 일 등 접촉 순서를 미리 구성한 것 |
| 데이터 보강 | 이메일, 직책, 회사 정보처럼 빠진 정보를 외부 자료로 채우는 일 |
| 티켓 | 해결해야 할 고객 요청 한 건과 그 처리 상태 |
| 고객 포털 | 고객이 직접 들어와 자기 자료와 진행 상황을 보는 공간 |
| 온보딩 | 계약한 고객이 서비스를 실제로 쓰기 시작하도록 준비하는 과정 |

용어 설명은 이 비교를 위한 쉬운 풀이이며, 각 제품의 데이터 구조가 완전히 같다는 뜻은 아니다. [Attio 데이터 모델](https://attio.com/help/reference/attio-101/attios-data-model/define-your-data-model-objects-lists-and-views), [Apollo 시퀀스](https://knowledge.apollo.io/hc/en-us/articles/4409231193101-Create-a-Sequence), [Assembly 고객 화면](https://assembly.com/docs/core-concepts/your-portal), [Arrows 고객 계획](https://help.arrows.to/en/articles/9815297)

## 우리 상황에서 제품을 비교할 기준

처음부터 화면 수나 기능 수로 순위를 정하지 않는다. 아래 질문에 실제 거래 예시를 넣어 답해 본다.

1. 고객별 요청과 이번 작업의 조건을 구분해서 볼 수 있는가?
2. 자주 쓰는 작업 항목을 재사용하면서 예외도 쉽게 바꿀 수 있는가?
3. 항목별 가격과 협의한 총액을 어떤 방식으로 표현하는가?
4. 금액의 포함·별도 기준이 바뀌면 이전 합의와 수정 내용을 어떻게 확인하는가?
5. 이 일을 하려면 먼저 얼마만큼의 설정과 입력이 필요한가?
6. 고객에게 전달할 결과물이 메모인지, 견적서인지, 계약서인지, 고객용 화면인지?

이 질문은 구매 추천이나 최종 요구사항 확정이 아니라 참고 제품을 고르기 위한 평가 기준이다. 세금 관련 예시는 합의한 금액의 의미를 정확히 기록하는 문제로 다루며, 세율이나 세무 처리 정책은 여기서 정하지 않는다.
